# 未来予測アドバイザリー (Foresight)

根拠: neco「Diの議論に『未来予測』を入れる」(2026-10-18)、同日「未来予測はオプショナルのアドバイザリーとしてやる。
結論は最後なのでその順番で良い」。
イノベーション理論をベースに、現行のプロダクトライフサイクルを破壊可能な一手を提案し、
その一手と帰結を「賛同 (改革派)」「否定 (保守派)」の視点から議論させ、最後にその結果訪れる
3 / 5 / 10 年後を予測する。ビジネススキームなら利益率・確度・ノウハウの強度も分析する。

2026-10-18 に Fable / Astra が仕組みを評価し (Ludellus の議論で 1 回走らせた出力を材料にした)、
neco の指示で指摘の ①〜⑦ をすべて反映した (理論の適用条件 / 本議論の文脈の受け渡し / 条件付きシナリオ /
完了表示の分離 / 陣営の独立と往復の段階 / 勝敗ではなく未解決の前提 / 失敗・境界条件のテスト)。

## オプショナル / アドバイザリー

- **観点タグ「未来予測」を付けた議論だけで走る** (`wantsForesight`、`src/flow/tags.ts`)。
  - Discord: 議論フォーラムのタグ「未来予測」(他の観点タグと一緒に自動で用意される)。
  - Web `/flow`: 開始フォームとペーパー編集のタグ欄「未来予測 (アドバイザリー)」。
- **結論を変えない参考**。prompt で「本議論の結論を覆したり書き換えたりしない」と指示し、
  投稿の先頭とペーパーの見出しに「アドバイザリー (参考)」と書く。`conclusion` / `concluded` は変えない。
- 結論の通知 (Discord の「✅ 結論」) は従来どおり最後に出る (未来予測の後)。
- **本議論が収束しなかった (結論なし) ときは行わない**。土台の無いまま一手を作らせない。

## 位置

議論 (企画/議論・改善/議論) の**結論の後**に 1 ラウンド分のフェーズとして続く。
`dispatchFlow` の後段 (`src/flow/foresight/after-flow.ts` の `runWithForesight`) で付けるので、
エンジン (`flow.engine` = rounds / dialectic) に依らず同じ経路で走る。学習・壁打ちには付かない。

```
本議論 (ラウンド 1..N → 結論)
   ▼  (タグ「未来予測」があり、結論が出た時だけ)
[F1] 提案   進行役: 前提事実 / 理論の当てはめ / 破壊可能な一手 / 実行すると何が起きるか / リスク
   ▼
[F2] 議論   改革派 (賛同) と 保守派 (否定) が交互に。往復ごとに 成立条件 → 反証 → 確かめ方
   ▼
[F3] 予測   記録係: 未解決の前提 / 3年後・5年後・10年後 それぞれ 成立・限定的定着・撤退/吸収 のシナリオ
            + 先行指標 + 確からしさ (定義付き) + ビジネス分析 (ビジネススキームの時だけ、算定不能を許す)
   ▼
✅ 結論の通知 (Discord)
```

## 本議論の文脈 (提案と予測に渡す)

未来予測は議題と結論だけでなく、本議論の資料を受け取る (`ForesightContext`、`src/flow/foresight/prompts.ts`)。

- ディスカッションペーパー本文 (議題 / 議論内容 / 論点 / 議論の経過 = 止揚 / 結論)。未来予測の節は外し、
  6000 字を超える分は切る。
- 本議論と同じ外部の声の検索 (`listExternalVoices`) で議題に当たる声を 8 件まで (各 200 字)。
  「議題との関連は未確認。関係の無いものは使わない」と注記して渡す。

市場規模・競合の機能・制度を取りに行く経路は持たない。代わりに、資料に無い事実は「未確認」と書かせ、
数値を作らせない (`EVIDENCE_LINE`)。

## 理論の土台 (適用条件つき)

理論名の列挙ではなく、当てはめてよい条件を prompt に入れる (`THEORY_CARDS`)。

- 破壊的イノベーション (Christensen): ローエンド型 = 主流顧客が過剰供給されていて安く簡素な代替で足りる層がいる /
  新市場型 = 非消費者を特定できる。どちらも既存企業が追わない収益構造が要る。安い・簡素・新しいだけでは破壊ではない。
  性能を上へ伸ばすのは持続的イノベーション。
- プロダクトライフサイクル: 市場単位 (製品カテゴリ / 個別製品 / 企業) を決めてから段階を判定。根拠が無ければ「未確認」。
- 普及理論 (Rogers): 採用時期の区分で、無料 / 有料の区分ではない。
- キャズム (Moore): Rogers とは別の理論。越えるには参照事例とホールプロダクトが要る。
- 当てはまる型が無いときは「当てはまらない」と書いてよい。

提案の見出しは判定を先に求める (【前提事実】確認済み / 仮説 / 不明 → 【理論の当てはめ】→ 一手)。
「何を過剰に供給しているか」のように過剰供給を前提にした問いは使わない。

## 話者 (`src/flow/foresight/camps.ts`)

本議論の発話から話者を引き継ぐ (新しく生成しない)。

- **陣営は本議論の賛否と独立**: 進行役以外の話者を初登場順に 改革派 → 保守派 → 改革派 … と交互に割り当てる
  (本議論の命題への賛否と、提案された一手への賛否は別の問い)。prompt でも「本議論での自分の賛否とは独立に」と指示する。
- 各話者は本議論での自分の直近の発言 2 件 (各 240 字) を持ち、視点と口調の参考にする (立場は縛られない)。
- エラー発話しかない話者は入れない
- 進行役は本議論の facilitator。居なければ代役「進行役」
- 進行役以外の話者が 2 人未満ならフェーズを行わない
- 話者順は改革派から交互、各陣営の中は巡回
- **発言回数は往復単位** (`normalizeCampTurns`): 偶数に切り上げ、最低 1 往復。turns=1 でも保守派が話す。
- **往復ごとの論点** (`campStageAt`): 1 往復目 = 成り立つ条件、2 往復目 = 反証 (崩れたら主張が成り立たなくなる前提)、
  3 往復目以降 = 確かめ方 (誰が・何を・どの期間で観測すれば白黒つくか)。言い換えを禁じ、新しい根拠か条件を 1 つ以上求める。

発話の stance は `reform` / `conservative` (表示名は「名前 (改革派)」「名前 (保守派)」)。
提案と予測は進行役の `neutral`。

## 予測の形式

- **勝ち負けは判定しない**。【未解決の前提】に、決着しなかった前提ごとの 改革派の見方 / 保守派の見方 /
  白黒をつける観測 (何を・いつまでに) を並べる。
- 3 / 5 / 10 年は時点。各時点で 成立 / 限定的定着 / 撤退・吸収 の 3 シナリオと、どれに進んでいるかを見分ける
  先行指標 (何を観測し、どの値・状態ならどれか) を書く。成功の筋書きを前提にしない。
- 確からしさの定義 (較正された確率ではない): 高 = 主要な前提が確認済み事実で支えられ反証の兆しが無い /
  中 = 一部が仮説 / 低 = 多くが仮説か議論で崩れかけた / 判定不能 = 材料が無い。
- ビジネス分析: 利益率 (高 / 中 / 低 / 算定不能)、確度 (高 / 中 / 低 / 判定不能)、ノウハウの強度
  (高 / 中 / 低 / 算定不能。保有済みと形成見込みを分け、競合が別の手段で同じ成果を出せるかも書く)。
  価格・原価・獲得費・運用費などの材料が無ければ「算定不能」とし、要るデータを書く。
- 予測は議論役と別のモデルにできる (`forecastModel`)。書き手が議論の当事者にならないようにするため。

## 記録と表示

- 発話は本議論と同じ `flow_utterance` に永続し、`onUtterance` で Discord / Web へ流す。
  round は本議論の最終ラウンド + 1、turn は通し番号。
- 提案の先頭は `🔮 未来予測アドバイザリー (参考): 破壊的な一手の提案`、
  予測の先頭は `🔭 未来予測アドバイザリー (参考): 3 / 5 / 10 年後`。
- 1 発話が 1780 字 (コードポイント) を超える時は行単位で分けて複数の発話にし、末尾に `(n/m)` を付ける
  (Discord webhook は 1900 字で切るため。サロゲートペアは割らない)。
- ペーパー本文 (`body_md`) の末尾に「# 未来予測アドバイザリー (参考)」節 (提案 + 未解決の前提とシナリオ) を焼く。
  付け直しは前の節 (初版の見出し「# 未来予測」も含む、本文の先頭にあっても) を外してから (やり直しでも重ならない)。
- `FlowDirectorResult.foresight` に `{ proposal, forecast }` を載せ、発話は `utterances` に足す。

## 進行状態と完了表示 (`src/flow/foresight/state.ts`)

本議論の結論 (`flow_conclusion`) は未来予測より前に書かれるので、結論の有無だけで完了にすると、
未来予測の実行中も完了に見える。sessionId ごとに状態を持ち、Web の status はこれを見る。

| state | 意味 |
|---|---|
| `pending` | 本議論の実行中 (終わったら未来予測を行う予定)。sessionId が先に分かる経路 (Web) で記録 |
| `running` | 未来予測を実行中 |
| `done` | 提案・議論・予測がすべて出た |
| `skipped` | 行わなかった (本議論が未収束 / 話者不足)。理由を detail に持つ |
| `degraded` | 一部の発言・予測・ペーパー追記が失敗した (出たものは記録済み) |
| `failed` | 提案が出ず止めた / フェーズが例外で止まった / 本議論が例外で止まった |

- `GET /api/flow/:session/status` は `foresight: { state, detail? } | null` を返し、`pending` / `running` の間は
  `done=false` にする。`/flow` 画面は実行中に「結論あり / 未来予測アドバイザリーを生成中…」、完了時に状態を出す。
- 状態はプロセス内メモリで永続しない。実行中の未来予測はプロセスと一緒に消えるので、再起動後は状態なし
  (= 走っていない) として扱う。
- Discord は `dispatchFlow` の完了後に結論を通知するので、この問題は起きない。

## 失敗時

- LLM 失敗は発話にエラーを出して続ける (OVERVIEW §10)。空応答の発言は投稿せず失敗に数える。
- 提案が出なければ (失敗 / 空応答) 以降を行わない (`failed`)。
- 発言・予測・ペーパー追記の失敗は `degraded` に数える。
- フェーズ全体の例外は warn して本議論の結果をそのまま返す (議論を壊さない、`failed`)。

## 設定 (`config.flow.foresight`)

| キー | 既定 | env | 説明 |
|---|---|---|---|
| `enabled` | `true` | `DISCUTERE_FLOW_FORESIGHT_ENABLED` | 機能ごとの有効化。false ならタグがあっても走らない |
| `turns` | `6` | `DISCUTERE_FLOW_FORESIGHT_TURNS` | 改革派 / 保守派の発言回数 (1..20、往復単位に切り上げ) |
| `model` | `""` | `DISCUTERE_FLOW_FORESIGHT_MODEL` | 提案と議論に使うモデル (空なら LLM の既定) |
| `forecastModel` | `""` | `DISCUTERE_FLOW_FORESIGHT_FORECAST_MODEL` | 予測だけに使うモデル (空なら `model`) |

LLM コストはタグ付きの議論ごとに 提案 1 + 議論 `turns` (往復単位) + 予測 1 回増える。
提案と予測の prompt にはペーパー本文 (最大 6000 字) と声 8 件が載る分、入力トークンが増える。
