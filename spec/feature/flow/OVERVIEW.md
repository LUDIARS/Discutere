# 議論フロー (4 フロー) — ドメイン概観

> 状態: ドラフト (2026-06-13)。議論精度向上のための再設計。
> 関連実装 (現状): `src/discussion/` (DiscussionDirector) / `src/persona-engine/`
> (rule engine + facilitator) / `src/crawler/sentiment/` (感情) / `src/db/`。

Discutere の「議論」を **4 つのフロー** に分けて定義するドメイン。本書は共通の
ユビキタス言語・設定・横断仕様 (ディスカッションペーパー / タグ / コストログ /
ロール別配布 / RAG) を定義し、各フローの詳細は個別 spec へ橋渡しする索引。

| フロー | spec | 一言 | LLM 議論 | 実装順 |
|---|---|---|---|---|
| **議論** | [discussion.md](./discussion.md) + [dialectic.md](./dialectic.md) | テーマに対し AI が複数ラウンドで意見をぶつけ結論を出す。議論の「中身」(論証状態/止揚/収束) は弁証法エンジン spec に規定 (2026-07-02) | あり | **① 最初に作る** |
| **改善** | [improvement.md](./improvement.md) | 議論と同骨格。投票/感情評価を **機械計算** に置換 | あり | ② |
| **学習** | [learning.md](./learning.md) | テーマ即応のユーザ意見/メカニクスを発話・記録 (議論しない) | なし | ③ |
| **壁打ち** | [sparring.md](./sparring.md) | ユーザターン起点・不定期発話・上限付き無制限ラウンド | あり | ④ |

> **横断原則**: すべての議論 (4 フロー全部) の成果物・発話は **次の議論の学習データ**
> として KG / コーパスに蓄積される (§7)。

## 1. ユビキタス言語

| 用語 | 定義 |
|---|---|
| **テーマ (議題)** | 議論の起点。人間または AI が投入する 1 つの問い。タグを伴う (§3)。 |
| **ラウンド** | 1 回の議論のまとまり。複数のターンの集合。ラウンド終了時にファシリテーターが一度まとめ → 投票フェーズに入る。 |
| **ターン** | 誰か 1 人が 1 回発言すること。= 1 意見。ターンごとに発言者をルールエンジンが割り当てる (§4)。 |
| **投票** | 「どの意見がテーマに対し的を射ているか」を判定し、**良い意見を 1 つ選んでリアクション**する行為。中立性を保つため**ペルソナを注入しない**。投票で得た票数 = **世論** = そのラウンドの主要意見。 |
| **世論** | 投票で支持を集めた意見。投票数が多いほど「そのラウンドの主要意見」として扱う。 |
| **ロール** | 議論内での立場。現状の Di を踏襲: **ファシリテーター / 賛成派 / 反対派 / 意見屋**。**賛否はセッション開始時に固定** (2026-07-02 改訂。毎ターン再抽選は人格の立場一貫性を壊すため廃止。各ペルソナは価値軸を持つ — [01](../../plan/20260702_respec_from_fable/01-persona-state.md))。 |
| **ディスカッションペーパー** | 各エージェントに配布する資料。テーマ + メカニクス + タグ補足 + 前ラウンド結果を束ねる。ロール × LLM 性質で内容が変わる (§5)。 |
| **止揚 (アウフヘーベン)** | 対立を統合した新しい結論。ラウンドサマリ時に検出され、ディスカッションペーパーに追記される (現 `aufhebung_stock`)。 |
| **想定意見データ** | 機密テーマで実ユーザ意見が使えない時に、メカニクス評価から事前合成する代替意見 (§5.4)。 |

## 2. 共通設定 (外部から人間が設定可能)

すべて `discutere.config.json` / env で設定する (現 `config.discussion` を拡張)。
解決順は既存どおり default < config ファイル < env。

| 設定 | キー (config) | 意味 | 備考 |
|---|---|---|---|
| **ラウンド数** | `flow.rounds` | 議論を進める最大ラウンド数 | 現 `discussion.maxRounds` を流用/改名 |
| **ターン数** | `flow.turnsPerRound` | 1 ラウンドあたりのターン数 | 現 `discussion.expectedUtterances` に相当 |
| **議論参加ペルソナ人数** | `flow.personaCount` | 議論プレイヤーの人数 | 現 composition の総数算出を置換 |
| **投票参加人数** | `flow.voterCount` | 投票フェーズの投票者数 | 新規。中立投票者の数 |
| **タグ** | `flow.tags[]` / テーマ単位 | `機密` `内部` `運用` `開発` 等 | §3。テーマ受信時に付与 |

> 既存の `config.discussion.*` (keymanCount / opinionModels / turnDelayMs /
> continueTimeoutMs 等) はモデル編成・進行ペースの設定として併存させる。本ドメインの
> `flow.*` は「フロー共通の進行量」を司る (議論の駆動は新規 FlowDirector、§4)。既存
> `config.discussion.*` は**併存**させモデル編成・ペース設定として流用する。

## 3. タグ (機密 / 内部 / 運用 / 開発)

テーマに付くメタ。**外部データ収集の可否**と**ディスカッションペーパーの補足内容**を
決める「機密度 + 観点」タグ (現状の Di に無い新規概念)。Discord ではこれらも**フォーラムの
適用タグ**として付与する (議論タイプ選択と同じ仕組み、§9)。意味は既存の方向タグ (現
`discord.forum.improvementTagNames` / `funTagNames`) とは別。

| タグ | 外部収集 (YouTube/Steam) | ディスカッションペーパー補足 | 備考 |
|---|---|---|---|
| (なし) | 可 | 標準 | |
| **開発** | 可 | 開発者観点 (設計意図/実装コスト) を補足 | |
| **運用** | 可 | 運用者観点 (継続率/収益/負荷) を補足 | |
| **内部** | **不可** | 標準 + 内部前提 | 外部検索しない |
| **機密** | **不可** | **想定意見データ**を充てる (§5.4) | 外部検索しない + ユーザ意見欠落の代替 |

- 複数タグの併用可 (例 `開発` + `機密`)。**収集可否は最も厳しいタグが優先** (`機密`/`内部`
  があれば収集しない)。
- タグは保管層では監査用に保持するが、露出面では既存の匿名化方針 (`CLAUDE.md` 個人データ
  方針) に従う。

## 4. 駆動方式・ロール・ターン割り当て

- **駆動は新規の FlowDirector** が担う。ターン駆動。**発言者はシャッフル輪番**
  (2026-07-02 改訂。ラウンド開始時に rng シャッフル → 巡回、全員の発言機会を保証。
  旧「ランダム選択」は発言機会の偏りと pro/con 不在ラウンドを生むため廃止 —
  [02](../../plan/20260702_respec_from_fable/02-turn-scheduling.md))。dialectic エンジン
  ([dialectic.md](./dialectic.md)) では論証状態に基づく指名制。
  ペルソナは議論ごとの使い捨てだが、**キャスト (stance/価値軸) は `flow_session_persona` に
  永続**し再現性・レビューを可能にする。
- **persona-engine (ルールエンジン) は本フローでは使わない**。persona-engine は Concordia の
  チャット駆動エンジン由来で、そもそもターンベース議論に向かないため議論フローから外す。
  ただしルールエンジン自体は利用価値があるので**今後の参考材料としてリポジトリに残す**
  (現状はそこまでの高級実装は不要)。
- ロール構成は **ファシリテーター / 賛成派 / 反対派 / 意見屋**。賛否 (賛成派/反対派) は固定
  せず**ターン時に決定**する。
- ファシリテーターはテーマ出題・ラウンドまとめ・収束/結論判定を担う (既存
  `src/persona-engine/facilitator/` の止揚・要約ロジックは**関数として流用**してよい。engine
  としては起動しない)。

## 5. ディスカッションペーパー

各エージェントに配布する議論資料。**ロール × LLM 性質で内容が変わる**。前ラウンドの
結果が追記されていく可変ドキュメント (1 テーマ = 1 ペーパー、ラウンドごとに成長)。

### 5.1 共通項目 (全ロール共通)

- **テーマ (議題)**
- **ゲームのメカニクス** (現 Discatier Core の `mechanics` / `data/games/<slug>.md`)
  - **(2026-07-02 改訂)** メカニクスは**出所ラベル** (`curated` / `llm` / `crawl`) を持ち、
    LLM 増補分は **`# 仮説メカニクス (LLM抽出・未検証)`** として節分離する。共通地盤に
    未検証の生成物を curated と同格で混ぜない
    ([08](../../plan/20260702_respec_from_fable/08-paper-provenance.md))。
- **タグ補足** (§3。運用/開発などの観点差を明記)
- **前ラウンドの結果** (ラウンドサマリ + 止揚意見。§7 で追記される)
- **論点** (2026-07-02 追加。ペーパーレビューゲートで分解・人間承認した争点 3〜5 個。
  [09](../../plan/20260702_respec_from_fable/09-paper-gate-debatability.md))

> **ペーパーの性格 (2026-07-02)**: 「情報を厚く盛ったドシエ」ではなく
> **「出所が明示された薄い共通地盤 + 承認済みの論点リスト」**。証拠 (外部の声) は
> ペーパーに詰めず、必要時 (事実対立の解消・意見屋の参照) にオンデマンド RAG で引く。

### 5.2 ロール別の追加配布

| ロール | 共通項目に加えて渡すもの |
|---|---|
| **賛成派** | なし (共通項目のみ) |
| **反対派** | なし (共通項目のみ) |
| **意見屋** | **ユーザ意見のまとめ** (YouTube/Steam 意見のランダム抽出) を参考値として |
| **ファシリテーター** | ラウンド進行に必要な全文脈 (発話履歴 + 感情仕分け結果。後者はペーパーには載せない、§改善6) |

### 5.3 LLM 性質による上書き (ローカル LLM 特例)

- **ローカル LLM (Gemma 等、`llm.backend=local`)** が担うペルソナは、自己判断材料が
  少ないため、**ロールを問わず** RAG として**ユーザ意見のランダムチョイス**を渡してよい
  (賛成派/反対派でも可)。= §5.2 の「賛成派/反対派には何も渡さない」を**ローカル LLM が
  上書き**する。
- RAG の実体は現 `listRelevantExternalVoices` (出所付き・個人仮名、`CLAUDE.md` §14) を流用。

### 5.4 機密テーマの特例 (想定意見データ)

- `機密` タグでは実ユーザ意見が欠落するため、**事前にメカニクス評価を用いた「想定意見
  データ」**を用意して意見屋/ローカル LLM の参考値に充てる。
- 想定意見データはメカニクスの `intended_affect` / `intends` (現 schema) から合成する。
- **合成意見は「想定 (synthetic)」と明示タグ付け**し、実音声と無言で混在させない。`機密`
  テーマの結論出力は「想定意見ベース (実ユーザデータ無し)」と明記する (設計意図の自己検証に
  ならないよう、由来を透明にする)。

## 6. RAG 許可ルール (まとめ)

| 条件 | RAG (ユーザ意見検索) |
|---|---|
| 意見屋 | 許可 (参考値として配布) |
| 賛成派 / 反対派 (クラウド LLM) | 不許可 |
| 任意ロール (ローカル LLM) | 許可 (§5.3) |
| ゲーム機能/特定機能の感情検索 | ターン中に**場合により許可** (議論フロー step 5-1) |
| `機密`/`内部` タグ | 外部の新規収集は不可 (既存 KG 内の想定意見データのみ) |

## 7. 学習データ化 (横断)

- **すべての議論は次の議論の学習データになる**。発話・ラウンドサマリ・止揚・投票結果・
  結論を KG (Discatier Core) / コーパスに永続する。
- 学習フロー (§learning) は議論の**前段**でユーザ意見/メカニクスを仕込む役割。

## 8. コスト計測 (横断・必須)

コスト懸念に対し、**どこで・どれだけ LLM コストが出ているか特定可能**にする。

### 8.1 transcript_log (全議論)

- すべての議論について、LLM の **transcript (プロンプト + 応答全文)** をログデータとして残す。
- 粒度: 1 LLM 呼び出し = 1 レコード。フロー / セッション / ラウンド / ターン / ロール /
  ペルソナと紐付ける。

### 8.2 発話ごとのコストログ

1 回の発話 (= 1 ターン) にかかった LLM について以下を残す:

| 項目 | 内容 |
|---|---|
| **使用箇所** | どの LLM 呼び出しか (分類器 #1 / ファシリテーター #2 / ペルソナ発話 #3 / 投票 / 要約 / 感情カスケード)。現 OVERVIEW の「LLM は 3 か所」+ 投票/要約を含む |
| **時間** | 呼び出しのレイテンシ (ms) |
| **トークン量** | input / output トークン (現 `TokenUsage { input_tokens, output_tokens }` を永続化) |
| **モデル / backend** | 使用モデル ID と backend (anthropic / claude-cli / local / worker-pool) |

> 現状 `usage?: TokenUsage` は invoke 戻り値に乗るが**永続化されていない**。本仕様で
> 専用テーブル (例 `llm_cost_log` / `transcript_log`) に書き出す。

### 8.3 プライバシー / 保持方針

- transcript_log / コストログは**内部の検証用**で、外部公開しない。よって**プライバシーは
  ある程度緩くてよい** (transcript への出力マスクは不要)。
- ただし**必要のない情報は保持しない**。コスト特定に要る項目 (§8.2) と検証に要る transcript に
  絞り、目的外データは残さない。
- backend によってはトークン数を返さない (claude-cli / worker-pool)。取得不能な値は null 許容
  (best-effort)。

## 9. 起動経路 (フローのトリガ)

議論の**最初の投稿**がトリガー。起点は **2 経路**:

1. **Di の簡素な WebUI** (loopback の 1 ページ。現 `spec/feature/web-chat.md` の `scene=web:` 系を流用)。
   テーマ入力時に**議論タイプ (フロー) を必須選択** + タグ選択。
2. **Discord のフォーラム投稿を UI とする** (現 Gateway / フォーラム starter / `forum-monitor` を流用)。
   フォーラムの**適用タグ**から **議論タイプ (フロー) とタグ (機密/内部/運用/開発) の両方**を取得する。
3. **Slack (Socket Mode)** (`src/slack/`, 2026-06-16 実装)。公開 URL 不要の常時 WS。設定チャンネルへの
   トップレベル投稿をテーマに、スレッドへ Block Kit の select で議論タイプ → 進行量を選んで起動する。
   発話は `chat.postMessage` を persona 表示名で投稿、投票は `reactions.add` で可視化 (§12)。
   有効化は `slack.enabled` + `slack.appToken`(xapp-) + `slack.botToken`(xoxb-) + `slack.channelIds`。

- **議論タイプ (議論 / 改善 / 学習 / 壁打ち) はテーマ投稿時に必須選択**。WebUI は選択 UI、Discord は
  フォーラムタグで指定する。
- **壁打ちもこの議論タイプ選択で判断する** (発話内容からの自動判定ではなく、投稿時にフローとして
  選ぶ)。壁打ち選択時のみ §sparring の進行 (ユーザターン起点・上限付き・「まとめて」/「おわり」) に入る。
- どの経路でも最初の投稿をテーマとして受信し (§discussion step 1)、タグ + 議論タイプを伴ってフローに入る。

## 10. 失敗時の扱い (横断)

- LLM 呼び出し・外部取得 (YouTube 等)・投票・要約などが失敗したら、**エラーログをちゃんと出す**。
- かつ**発話にもエラーを出す** (該当ターン / フェーズの出力としてエラー内容を提示し、失敗が
  議論の場に見えるようにする)。握り潰さない。

## 11. 決定ログ (2026-06-13)

旧「未確定論点」はすべて決着:

- **(a) 駆動エンジン**: persona-engine は使わず、新規 FlowDirector がターン駆動でその場生成
  ペルソナをランダム選択 (§4)。persona-engine は今後の参考材料として残す。
- **(b) 投票 / 感情評価**: 既存実装 (リアクションスコア等) は採らない (結果整合性のパラドックスを
  起こすため)。投票 = 中立 N 人が良い意見を 1 つ選ぶ。**改善フローでは機械スコアが世論決定権を持つ**。
- **(c)/(e) 目標ベクトルと評価**: 目標感情ベクトルの出所はメカニクスの `intended_affect`。
  「感情曲線」という表現は破棄。基本判定はベクトルの近さ (Di 基礎感情データがテーマ / 意見の
  どのベクトルに近いか、適合もベクトル近接で)。**改善フローは design_gap を計算**し
  「positive な改善ベクトルが計算結果として現れること」をスコアにする (§improvement)。
- **(d) コスト / transcript スキーマ**: 内部検証専用・外部非公開ゆえプライバシーは緩め、不要
  情報は持たない (§8.3)。
- **swapHalf 廃止**: 全メンバーをその場生成するため不要。
- **prompt-builder**: 当ラウンド優先のコンテキストスコープ変更で対応 (§discussion step 8)。
- **結論 (step 9)**: 既存の結論ビュー (`src/visualize/conclusions.ts`) に倣ってまとめる。

## 11.5 決定ログ (2026-07-02 — Fable セッションレビュー反映)

議論エンジンの正直レビュー (実態が「同一モデルによる独立したワンライナー生成の列」に
近い問題) を受けた再設計。詳細・対応表は
[`spec/plan/20260702_respec_from_fable/`](../../plan/20260702_respec_from_fable/README.md):

- **stance セッション固定 + 価値軸** (§1 ロール改訂)。`decideStance` の毎ターン再抽選は廃止。
- **シャッフル輪番** (§4 改訂)。ランダム選択は廃止。dialectic エンジンでは指名制。
- **レンズ投票**: 中立 N 人の同一プロンプト投票は実質 1 票のため、評価レンズ + 候補順
  シャッフル + 番号回答受理に改訂 (§11-b の中立投票の枠組み自体は維持)。
- **弁証法エンジン ([dialectic.md](./dialectic.md)) を新設**: 議論を論証状態機械として持ち、
  止揚は「LLM 判定」ではなく「生成 + 敵対的批准」のイベントにする。折衷と止揚を区別する。
  `flow.engine = "dialectic" | "rounds"` で切替。導入時は既定 rounds の opt-in、
  **2026-07-03 に既定を dialectic へ昇格** (rounds はフォールバックとして併存)。
- **改善フローのスコアは効果予測へ** ([improvement.md](./improvement.md) 改訂): 意見文面の
  感情ではなく「採用した場合の体験変化の予測」を design_gap へ射影する。
- **ペーパー = 出所明示の薄い共通地盤** (§5.1 改訂) + **議論適性ゲート** (争点の存在 /
  両論武装可能性 / 証拠バランス)。論点分解をレビューゲートに前倒しし人間が承認する。

## 12. 議論精度・UX 改善 (2026-06-16)

ユーザ要望に基づく 7 点の改善。トランスポート非依存の表示/投票/憑依ロジックは `src/flow/` に集約し、
Discord (`src/flow/discord-live.ts`) と Slack (`src/slack/slack-live.ts`) の両露出面で共有する。

1. **進行量を議論ごとに毎回設定 (item1)**: WebUI (`/flow`) は数値入力。Discord/Slack は議論/改善の起動前に
   進行量 (ラウンド×ターン) の **select (プリセット) + 数値モーダル** を出して都度指定する。本文記法
   `ラウンド:N ターン:M` での明示指定があればそれを優先 (UI スキップ)。上限は `MAX_ROUNDS`/`MAX_TURNS_PER_ROUND`。
2. **表示名「名前 (ロール名/憑依ペルソナ)」(item2)**: `src/flow/persona-display.ts` の `composeDisplayName`。
   ロール名はそのターンのスタンス (賛成派/反対派/意見屋/進行役)。憑依が無ければ括弧内はロールのみ。
3. **投票をリアクションで可視化 (item3)**: ラウンド投票後 `onVote` 通知 → 世論に 🏆、得票意見に 👍 を付け、
   得票集計テキストをスレッドに投稿。LLM 投票者は実ユーザではないため「得票数=リアクション可視化 + 集計」で表す。
4. **憑依の可視化 (item4)**: 憑依は casual 生成ペルソナ名を保ったまま、データ由来ペルソナの人物像 (descriptor)
   を prompt に注入し、表示名の括弧内とログに憑依対象名を出す。`flow_utterance.possession_name` に永続。
5. **発話時の DB 参照キャッシュ (item5)**: `src/flow/voice-cache.ts`。同一テーマ/語の外部の声 lookup を
   セッション内で 1 回に集約し、全ペルソナのターンで使い回す。
6. **Slack 対応 (item6)**: §9-3 (Socket Mode)。
7. **匿名ペルソナの取込と採用 (item7)**: Voluptas が生成した匿名ペルソナは、HMAC 仮名化済みの
   `user_id` を同一人物アンカーとして `flow_persona` に upsert する。Di は質問票や回答からペルソナを
   生成しない。公開レビュー話者については既存 C1 採用 (`runAdoptFromKg`) を維持し、SteamID 等の公開
   platform ID を同一人物アンカーとして `論者#xxxxxx` へ仮名化する。
