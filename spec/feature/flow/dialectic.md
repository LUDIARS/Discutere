# 弁証法エンジン (Argument-State Engine)

> 状態: ドラフト (2026-07-02)。議論フロー ([discussion.md](./discussion.md)) の
> 「議論の中身」を規定する正本 spec。実装設計は
> [`spec/plan/20260702_respec_from_fable/`](../../plan/20260702_respec_from_fable/README.md)。
> 共通仕様 (タグ / ペーパー / コストログ) は [OVERVIEW.md](./OVERVIEW.md)。

## 0. 設計原理

議論を **発話の列** ではなく **論証の状態機械** として持つ。

- 現行 (rounds エンジン) は「発話ログ → LLM 要約 → LLM 止揚判定 → 件数で収束」という
  テキスト→テキストのパイプラインで、ターン間に持ち越される状態が生テキストしかない。
  止揚も収束も「テキストの山を LLM に眺めさせて雰囲気で判定」になっており、
  **LLM は頼めばいくらでも『それっぽい統合文』を書くので、生成できたこと自体に情報量がない**。
- 本エンジンは議論の進行につれて育つ **明示的な論証状態** (Issue / Position / Tension /
  Synthesis) を中心に据え、**状態遷移・スケジューリング・収束判定は決定的なコード**が持つ。
  LLM がやるのは **生成** (主張・反論・止揚候補) と **敵対的な批准** (accept/reject) だけ。

```
現行:  発話ログ ──(LLM要約)──> サマリ ──(LLM判定)──> 止揚? ──(件数)──> 収束
本書:  論証状態 (positions / tensions / syntheses)
          ↑ 発話 = 状態を変える「手」(dialogue act)
          ↓ ファシリテーター = 状態を見て次の一手を指名するディレクター
       収束 = 状態の計測値 (未応答論点=0, 票の集中, 新規論点の枯渇)
```

## 1. ドメインモデル

```
Issue (論点)           テーマから分解した争点。1 議論に 3〜5 個にクランプ。
 ├ Position (定立/反定立)
 │    claim     : 主張 1 文
 │    grounds[] : 根拠。各根拠が状態を持つ:
 │                unchallenged → challenged → (防御成功) defended / (放棄) conceded
 │    values[]  : 価値前提 (「収益 > 体験」等。Tension の型判定に使う)
 ├ Tension (矛盾)      対立する 2 Position の組 + 対立の「型」(§2)
 └ Synthesis (止揚候補)
      preserves[] : 各陣営から何を保存したか (根拠 ID で指す)
      negates[]   : 何を放棄させたか
      elevates    : 導入した新しい枠 (上位目標 / 条件分割 / 再定義)。空なら折衷 (§4)
      ratification: 両陣営ペルソナの受諾/拒否 + 理由
```

- 用語対応: 定立 = thesis、反定立 = antithesis、止揚 = aufheben
  (否定 negate / 保存 preserve / 高揚 elevate の三位一体)。3 要件をそのまま
  Synthesis のデータ要件にすることで、止揚が **検証可能なデータ** になる。

## 2. 対立の型 — 型が解法を決める

すべての対立が止揚の対象ではない。Tension は型分類され、型ごとに分岐する:

| 型 | 例 | 解法 | 止揚か? |
|---|---|---|---|
| **事実対立** (facts) | 「ガチャ緩和で売上は下がる/下がらない」 | RAG・データ照会で**解消** (resolution) | ✕ (検証問題) |
| **価値対立** (values) | 「収益性 vs プレイヤー体験」 | 上位価値の発見・**適用条件の分割** (コア層には X、ライト層には Y) | ○ |
| **手段対立** (means) | 目標は共有、手段が違う | 共通目標の再確認 → 手段の**合成・段階化** | ○ |
| **トレードオフ** (tradeoff) | 両立不能に見える 2 変数 | パラメータ化・**非線形の第 3 案** | ◎ 最も止揚らしい |

- **事実対立は弁証法のスコープから外す**。KG/RAG (`listRelevantExternalVoices`) へ照会して
  解消を試み、解消できなければ **「未解決の事実問題」として結論に明記**する (隠さない)。
- 型別に止揚生成プロンプトのテンプレートを変える (価値対立 → 条件分割を促す、
  トレードオフ → 第 3 案を促す、等)。

## 3. アルゴリズム (位相駆動)

一様な「ラウンド × ターン」ループを、弁証法の位相 (phase) に対応させる。
**状態遷移・スケジューリング・収束判定・修正ループ回数はすべて決定的なコード**が持つ。

```
[0] 論点分解      テーマ + ペーパー → Issues (3〜5 個)          … LLM 生成 ×1
                  ※ ペーパーレビューゲートに前倒しし人間が承認できる (§7)
[1] 定立          各 debater が issue ごとに Position を張る      … LLM 生成
[2] 反定立        相手の grounds/values を攻撃 (指名制・応答権付き) … LLM 生成
      └ コードが論証グラフを更新: ground の状態遷移
[3] 矛盾の特定    残った対立を Tension として型分類               … LLM 判定 (小モデル)
      └ 事実対立 → RAG 照会で解消試行。失敗は「未解決の事実問題」
[4] 止揚          型別テンプレートで Synthesis 候補を生成          … LLM 生成
      └ 批准: 両陣営ペルソナが accept/reject (敵対的, §5)        … LLM 判定 ×2 (小モデル)
      └ 部分受諾 → 修正ループ (コードが最大 2 回でカット)
[5] 収束判定 (コードのみ):
      open tension = 0、または残 Tension を「合意不能」と記録して結論へ
```

- スケジューラ (ファシリテーターの中身) は決定的: **未解決 Tension のうち論証グラフ上で
  最も接続数が多いもの**を次の焦点に選び、応答義務のあるペルソナを指名する。
  LLM は指名を自然な進行文にレンダリングするだけ。
- [2]⇄[4] は issue ごとに独立に回せる。露出面 (Discord/Web) には「論点 N: 〜について」
  という束で流れ、進行の体感は現行ラウンド制と大きく変わらない。

## 4. 折衷と止揚のゲート

`elevates` が空、または内容が「両方やる」でしかない Synthesis は
**折衷 (compromise) に格下げ**する。折衷も記録はする (価値はある) が:

- 止揚ストックに数えない
- 早期収束シグナルに数えない
- 結論では「折衷」と明記する

この 1 ゲートが「止揚カウント = 実質ラウンド数」という空洞化を防ぐ。

## 5. LLM 利用の 3 役分離

| 役割 | タスク | モデル / 温度 | 出力 |
|---|---|---|---|
| **生成** | Position / rebut / Synthesis 候補 | メインモデル・温度高め | 構造化 JSON + 露出用口語 1〜3 文 (表と裏を同時生成) |
| **判定** | Tension 型分類、elevation ゲート | 小モデル (Haiku 級)・温度 0 | 単一ラベル |
| **批准** | Synthesis の accept/reject | 小モデル・温度 0・**敵対的プロンプト** | チェックリスト回答 |

原則:

1. **生成と判定を同じ呼び出しに混ぜない** (現行 aufhebung judge = 生成兼判定、が創作の温床)。
2. **批准は「否定するインセンティブを持つ側」にやらせる**。中立審判に「妥当か」と聞くと
   同調バイアスで yes に流れる。元の pro/con ペルソナ (立場と grounds を保持) に、
   チェックリスト式・**reject デフォルト**で聞く:
   > あなたの主張の根拠は [G1, G2, G3] だった。この統合案で保存されているものを ID で
   > 挙げよ。保存が確認できた根拠が過半数に満たなければ reject し、欠けているものを指摘せよ。
   これにより「批准された止揚」は **両陣営の根拠の過半を明示的に保存している** ことが
   機械的に保証される。
3. **状態はダイジェストで渡す**。ペーパー base を system に固定するキャッシュ戦略は維持し、
   論証状態は「当該 issue の Position 2 つ + 未解決の challenge」だけを user 側に注入する。
4. 将来: 批准側にローカル LLM backend (`llm.backend=local`) を使いモデル系統を分けることで
   甘受諾バイアスをさらに緩和できる (opt-in)。

## 6. 収束と結論

早期収束は「止揚 N 件」(旧 `facilitator.aufhebungTarget`) ではなく、状態の計測値の多数決:

- (a) **未応答反論数** が 0 に向かっている
- (b) **投票の集中度** (最多得票シェアが閾値超え。投票はレンズ別 — discussion.md step 6)
- (c) **新規 claim の枯渇** (直近 K ターン新しい主張なし)

2/3 成立で収束。`aufhebungTarget` は上限キャップとしてのみ残す。

結論生成には以下を渡す (現行の「直近 20 発話のみ」を廃止):

- 各 issue の Position 対と決着 (批准済み Synthesis / 折衷 / 合意不能)
- 未解決の事実問題 (RAG 解消失敗分) — **結論に明記** (誠実性)
- ラウンド/フェーズサマリ + レンズ別投票の集中度

## 7. ペーパーとの接続

- **論点分解 [0] はペーパーレビューゲートに前倒し**する。md 正本に `# 論点` 節を持ち、
  人間が Notion 風ブロック編集で論点そのものを調整・承認できる
  (詳細: [paper gate spec 変更](../../plan/20260702_respec_from_fable/09-paper-gate-debatability.md))。
- ペーパーは「出所が明示された薄い共通地盤」(出所ラベル + 仮説メカニクス分離 —
  [08](../../plan/20260702_respec_from_fable/08-paper-provenance.md))。証拠は Tension 単位の
  オンデマンド RAG で引く (ペーパーに厚く盛らない)。

## 8. 正直な限界 (spec として明記)

- 本エンジンは弁証法を「実装」するのではなく、**弁証法的な手続きを「強制」する**もの。
  真に創造的な第 3 案 (elevates の中身) が出るかは生成 LLM の能力依存で、構造が保証するのは
  「出たものが検証可能で、出所が追える」ことまで。
- **論点分解 [0] の粒度が全体の質の上限を決める**。3〜5 個クランプ + 人間レビューゲートで補う。
- 事実対立の RAG 解消は KG 材料の質に律速される。解消失敗は隠さず結論に明記する。
- 批准者が同一モデル系である限り甘受諾バイアスは残る (緩和は §5-4)。

## 9. 移行方針

- 新エンジンは `flow.engine = "dialectic" | "rounds"` (既定 `rounds`) の config スイッチで
  導入し、既存 rounds エンジンは検証完了まで既定のまま併存させる。
- コスト水準: 1 issue あたり 8〜12 call (定立 2 + 反定立 ~4 + 分類 1 + 止揚 1〜2 + 批准 2〜4)、
  3〜4 issue で 30〜50 call。現行 (≈40 call) と同水準、判定系が小モデルに寄るぶん実コストは
  下がる余地がある。既存 `withCostLog` にそのまま乗せる。
