# 弁証法エンジン (Argument-State Engine)

> 状態: ドラフト (2026-07-02)。議論フロー ([discussion.md](./discussion.md)) の
> 「議論の中身」を規定する正本 spec。実装設計は
> [`spec/plan/20260702_respec_from_fable/`](../../plan/20260702_respec_from_fable/README.md)。
> 共通仕様 (タグ / ペーパー / コストログ) は [OVERVIEW.md](./OVERVIEW.md)。

## 0. 設計原理

議論を **発話の列** ではなく **論証の状態機械** として持つ。

- 現行 (rounds エンジン) は「発話ログ → LLM 要約 → LLM 止揚判定 → 件数で収束」という
  テキスト→テキストのパイプラインで、ターン間に持ち越される状態が生テキストしかない。
  止揚も収束も「テキストの山を LLM に眺めさせて雰囲気で判定」になっており、
  **LLM は頼めばいくらでも『それっぽい統合文』を書くので、生成できたこと自体に情報量がない**。
- 本エンジンは議論の進行につれて育つ **明示的な論証状態** (Issue / Position / Tension /
  Synthesis) を中心に据え、**状態遷移・スケジューリング・収束判定は決定的なコード**が持つ。
  LLM がやるのは **生成** (主張・反論・止揚候補) と **敵対的な批准** (accept/reject) だけ。

```
現行:  発話ログ ──(LLM要約)──> サマリ ──(LLM判定)──> 止揚? ──(件数)──> 収束
本書:  論証状態 (positions / tensions / syntheses)
          ↑ 発話 = 状態を変える「手」(dialogue act)
          ↓ ファシリテーター = 状態を見て次の一手を指名するディレクター
       収束 = 状態の計測値 (未応答論点=0, 票の集中, 新規論点の枯渇)
```

## 1. ドメインモデル

```
Issue (論点)           テーマから分解した争点。1 議論に 3〜5 個にクランプ。
 ├ Position (定立/反定立)
 │    claim     : 主張 1 文
 │    grounds[] : 根拠。各根拠が状態を持つ:
 │                unchallenged → challenged → (防御成功) defended / (放棄) conceded
 │    values[]  : 価値前提 (「収益 > 体験」等。Tension の型判定に使う)
 ├ Tension (矛盾)      対立する 2 Position の組 + 対立の「型」(§2)
 └ Synthesis (止揚候補)
      preserves[] : 各陣営から何を保存したか (根拠 ID で指す)
      negates[]   : 何を放棄させたか
      elevates    : 導入した新しい枠 (上位目標 / 条件分割 / 再定義)。空なら折衷 (§4)
      ratification: 両陣営ペルソナの受諾/拒否 + 理由
```

- 用語対応: 定立 = thesis、反定立 = antithesis、止揚 = aufheben
  (否定 negate / 保存 preserve / 高揚 elevate の三位一体)。3 要件をそのまま
  Synthesis のデータ要件にすることで、止揚が **検証可能なデータ** になる。

## 2. 対立の型 — 型が解法を決める

すべての対立が止揚の対象ではない。Tension は型分類され、型ごとに分岐する:

| 型 | 例 | 解法 | 止揚か? |
|---|---|---|---|
| **事実対立** (facts) | 「ガチャ緩和で売上は下がる/下がらない」 | RAG・データ照会で**解消** (resolution) | ✕ (検証問題) |
| **価値対立** (values) | 「収益性 vs プレイヤー体験」 | 上位価値の発見・**適用条件の分割** (コア層には X、ライト層には Y) | ○ |
| **手段対立** (means) | 目標は共有、手段が違う | 共通目標の再確認 → 手段の**合成・段階化** | ○ |
| **トレードオフ** (tradeoff) | 両立不能に見える 2 変数 | パラメータ化・**非線形の第 3 案** | ◎ 最も止揚らしい |

- **事実対立は弁証法のスコープから外す**。KG/RAG (`listRelevantExternalVoices`) へ照会して
  解消を試み、解消できなければ **「未解決の事実問題」として結論に明記**する (隠さない)。
- 型別に止揚生成プロンプトのテンプレートを変える (価値対立 → 条件分割を促す、
  トレードオフ → 第 3 案を促す、等)。

## 2.5 議論の前提ルール (2026-10-06)

当初は止揚だけを議論のゴールに置いていたため、相手の主張を曲げるために前提の外から攻める発言
(範囲外の反例・すり替え・中身に触れない却下) が多く出た。前提ルールを破る反論はコードとゲートで
論証グラフへ入れない。論点の結論は §4.5 (止揚 / 論破 / 結論なしのいずれか)。

**共通見解の前提** — AI 同士の議論は、次の 3 点について共通見解は取れている前提で進める
(すり合わせ直さない。施策の定義 = 主張は人間が行い、何の数字を改善したいかは算出しない):

- どんな体験をつくりたいか
- どんな施策 (アイデア) を試したいか
- 他のゲームではどうしているか、どうなっているか

**論拠の種類** (`Ground.kind`):

| 種類 | 形 |
|---|---|
| 演繹 (deduction) | この仕様を入れて、こういう人が遊ぶと、こういう体験になる |
| 帰納 (induction) | この仕様を入れている他のゲームでは、こういう体験になっていた |
| アブダクション (abduction) | こういう体験を作りたいから、きっとこういう仕様にしたら良い |

**トゥールミンの整理**:

- Position は `claim` (主張) と `qualifier` (限定 = どの層・どの条件の話か) を持つ。
- 根拠は `text` (データ) と `warrant` (論拠) を分けて持つ。データが正しくても論拠が誤れば主張は誤り。
- 反論 (rebut) は**トゥールミンモデルを満たしていれば有効**。反論自身の `data` (データ) と `warrant` (論拠) を持ち、
  `attack` = data / warrant / qualifier のどれを突くかを宣言し、data / warrant なら `groundId` で攻撃対象の根拠を指す。

**ゲート** (`src/flow/dialectic/rule-check.ts`):

1. トゥールミン検査 (コードのみ): Position への反論で、反論自身のデータか論拠が無ければ違反 (`incomplete`)。
   `attack` が無い、または data / warrant なのに未譲歩の根拠を指していなければ違反 (`unanchored`)。
2. 判定 LLM (`judgeModel`、`flow.dialectic.ruleCheck` 既定 true): 宣言した要素を相手の限定の内側で突いているかを
   単一ラベルで判定 — `out_of_scope` (限定の外側から全体否定) / `straw_man` (言っていない主張への置き換え) /
   `dismissal` (中身に触れない却下) / `topic_shift` (論点ずらし)。障害・ラベル不明は ok に倒す。
3. 違反した反論は発話としては残すが act を `question` に格下げし、根拠を challenged にしない。
   進行役が違反の理由を一言流す。

## 2.6 論拠の応酬 (2026-10-13)

議論は「論拠の投げ合い → 反論への論拠 → …」のサイクルを論述のベースにする
(`src/flow/dialectic/exchange.ts` = 状態、`exchange-runner.ts` = 進行、`exchange-prompt.ts` = 応答プロンプト)。
投稿の見た目 (ペルソナ名義の口語投稿・進行役の進行文) は従来と変えない。

1. **投げ合い (定立)**: 賛成・反対の各 debater が主張を 1 件投稿し、論拠 (データ + 論拠 + 種類) を **1〜3 件**作る。
   論拠は陣営交互に 1 件ずつ投稿する (賛成の論拠 1 → 反対の論拠 1 → 賛成の論拠 2 → …)。
2. **反論のサイクル**: 投稿された論拠には相手陣営 (同じ立場の debater のうち発言数最少) が答える。答え方は
   - **反論**: 反論も **論拠 1 件** (データ 1 + 論拠 1) で立て、突く要素 (データ / 論拠 / 限定) を宣言する。§2.5 のゲートを通った反論だけが論拠として数えられる
   - **認める**: 相手の論拠 (反論) を認める
   反論はそれ自体が論拠なので、元の論拠の持ち主の陣営が同じように答える。応答順は**幅優先**
   (投げ合った論拠すべて → それらへの反論すべて → …) で、どちらかの論拠だけが後回しにならない。
   反論への再反論の前だけ進行役が指名文を流す。
3. **まとめ**: 応答待ちの論拠が無くなったら (= 論拠が落ち着いたら) 進行役が「残った論拠 賛成 x/y・反対 a/b」を
   告げてまとめに入り、§4.5 の結論判定 (止揚 / 論破 / 結論なし) へ進む。

**決着の評価** (コードのみ・三値): ノードは成り立った反論が 1 つでもあれば `refuted`、上限で打ち切られたら
`contested`、それ以外は `standing`。定立の論拠の根拠状態へは次のように写す。

| 応酬の結果 | 根拠状態 |
|---|---|
| 反論を受けていない | `unchallenged` |
| 反論を受けたが崩れていない (再反論が成り立った / 打ち切りで決着つかず) | `defended` |
| 持ち主が反論を認めて崩れた | `conceded` |
| 反論に答えられなかった・再反論が崩れて崩れた | `challenged` |

- 打ち切り (`contested`) は最後に答えた側を勝たせないため根拠を崩さない。
- 有効な反論にならなかった応答 (LLM 障害・空応答・JSON 崩れ・§2.5 違反) は相手の論拠を崩さない (発言は `question` で残る)。
- 上限: 反論の深さ `flow.dialectic.argumentDepth` (既定 4、定立の論拠 = 0。その深さの反論には答えさせない)、
  issue あたり応答ターン `flow.dialectic.exchangeTurns` (既定 16。超えた応答待ちは打ち切り)。
  旧 `rebutTurns` (指名制の反定立ターン上限) は未使用だが設定互換のため残す。
- 論証グラフ (`argument-graph.ts`) では、反論への再反論で元の反論が応答済み (`defended`) になり、
  新しい反論の応答義務は元の反論者が負う。計測型収束 (§6) の「未応答反論 = 0」は打ち切りが残ると成立しない。

## 4.5 論点の結論 — 止揚 / 論破 / 結論なし (2026-10-13)

論拠をぶつけ合った結果 (§2.6)、論点の結論は次の **3 区分のいずれか**にする
(`src/flow/dialectic/outcome.ts`。論破の判定は `goal.ts`)。進行役は「止揚: …」「論破: …」「結論なし: …」の形で流し、
決着表 (ペーパーの経過・結論生成の入力) にも【止揚】【論破】【結論なし】のラベルを付ける。

| 順 | 結論 | 判定 | 記録 |
|---|---|---|---|
| 1 | **論破** — どちらかの意見が出なくなる | コードのみ。一方の根拠がすべて崩れた (`challenged` = 有効な反論に応答できなかった / `conceded` = 譲歩した)。双方崩れた場合も論破 | Tension を立てず、論点の決着に判定文を残す |
| 2 | **止揚** | 止揚ループ (§4 の折衷ゲート + §5 の敵対的批准) で両陣営が批准 | Tension `synthesized` |
| 3 | **結論なし** | 上のどちらにも至らない。理由を添える: 折衷止まり (`compromised`) / 批准不成立 (`agreed_disagree`) / 事実対立の照会結果 (`resolved` / `unresolved_fact`) | Tension の状態 + 理由 |

- 論破は事実対立の照会より前に判定する (根拠が崩れた側の主張は事実照会を待たずに決着)。
- 事実対立は照会で解消できても論点の結論は「結論なし」(照会結果を理由に添える)。未解決の事実問題は従来どおり結論本文に必ず明記する。
- 合意 (結論の同一性の判定、2026-10-07〜10-13) はゴールから外した。判定 LLM (`location=agreement`) は呼ばない。
  旧 `agreed` 行は読み出し互換のため残し、表示は「結論なし (旧方式の合意判定)」。
- すり合わせ (体験・施策・他ゲーム事例を揃える手順) は人間に必要な手順であり、ゴールに置かない。
  AI 同士の議論はそれらの共通見解が取れている前提で進める。
  2026-10-07 に一時導入したすり合わせ (`flow_alignment` / `aligned` / `partially_aligned`) は撤去済み (状態値は読み出し互換のみ)。

## 3. アルゴリズム (位相駆動)

一様な「ラウンド × ターン」ループを、弁証法の位相 (phase) に対応させる。
**状態遷移・スケジューリング・収束判定・修正ループ回数はすべて決定的なコード**が持つ。

```
[0] 論点分解      テーマ + ペーパー → Issues (3〜5 個)          … LLM 生成 ×1
                  ※ ペーパーレビューゲートに前倒しし人間が承認できる (§7)
[1] 定立          各 debater が issue ごとに Position (論拠 1〜3) を張り、論拠を陣営交互に投稿 … LLM 生成
[2] 論拠の応酬    相手の論拠に「反論 = 論拠 1 件」か「認める」で答える (幅優先・§2.6) … LLM 生成
      └ コードが応酬を評価し ground の状態へ写す。落ち着いたら進行役がまとめに入る
[3] 矛盾の特定    残った対立を Tension として型分類               … LLM 判定 (小モデル)
      └ 事実対立 → RAG 照会で解消試行。失敗は「未解決の事実問題」
[4] 止揚          型別テンプレートで Synthesis 候補を生成          … LLM 生成
      └ 批准: 両陣営ペルソナが accept/reject (敵対的, §5)        … LLM 判定 ×2 (小モデル)
      └ 部分受諾 → 修正ループ (コードが最大 2 回でカット)
[5] 収束判定 (コードのみ):
      open tension = 0、または残 Tension を「合意不能」と記録して結論へ
```

- 応答順 (ファシリテーターの中身) は決定的: 応答待ちの論拠を幅優先で 1 件ずつ取り出し、
  相手陣営の発言数最少の debater に答えさせる (§2.6)。LLM は指名を自然な進行文にレンダリングするだけ。
  旧スケジューラ (`scheduler.ts` の `scheduleNextTurn`: 未応答反論 → 接続数最大の Position への攻撃番 → 自由ターン)
  は 2026-10-13 に driver から外した。
- [2]⇄[4] は issue ごとに独立に回せる。露出面 (Discord/Web) には「論点 N: 〜について」
  という束で流れ、進行の体感は現行ラウンド制と大きく変わらない。

## 4. 折衷と止揚のゲート

`elevates` が空、または内容が「両方やる」でしかない Synthesis は
**折衷 (compromise) に格下げ**する。折衷も記録はする (価値はある) が:

- 止揚ストックに数えない
- 早期収束シグナルに数えない
- 結論では「折衷」と明記する

この 1 ゲートが「止揚カウント = 実質ラウンド数」という空洞化を防ぐ。

## 5. LLM 利用の 3 役分離

| 役割 | タスク | モデル / 温度 | 出力 |
|---|---|---|---|
| **生成** | Position / rebut / Synthesis 候補 | メインモデル・温度高め | 構造化 JSON + 露出用口語 1〜3 文 (表と裏を同時生成) |
| **判定** | Tension 型分類、elevation ゲート | 小モデル (Haiku 級)・温度 0 | 単一ラベル |
| **批准** | Synthesis の accept/reject | 小モデル・温度 0・**敵対的プロンプト** | チェックリスト回答 |

原則:

1. **生成と判定を同じ呼び出しに混ぜない** (現行 aufhebung judge = 生成兼判定、が創作の温床)。
2. **批准は「否定するインセンティブを持つ側」にやらせる**。中立審判に「妥当か」と聞くと
   同調バイアスで yes に流れる。元の pro/con ペルソナ (立場と grounds を保持) に、
   チェックリスト式・**reject デフォルト**で聞く:
   > あなたの主張の根拠は [G1, G2, G3] だった。この統合案で保存されているものを ID で
   > 挙げよ。保存が確認できた根拠が過半数に満たなければ reject し、欠けているものを指摘せよ。
   これにより「批准された止揚」は **両陣営の根拠の過半を明示的に保存している** ことが
   機械的に保証される。
3. **状態はダイジェストで渡す**。ペーパー base を system に固定するキャッシュ戦略は維持し、
   論証状態は「当該 issue の Position 2 つ + 未解決の challenge」だけを user 側に注入する。
4. 将来: 批准側にローカル LLM backend (`llm.backend=local`) を使いモデル系統を分けることで
   甘受諾バイアスをさらに緩和できる (opt-in)。

## 6. 収束と結論

早期収束は「止揚 N 件」(旧 `facilitator.aufhebungTarget`) ではなく、状態の計測値の多数決:

- (a) **未応答反論数** が 0 に向かっている
- (b) **投票の集中度** (最多得票シェアが閾値超え。投票はレンズ別 — discussion.md step 6)
- (c) **新規 claim の枯渇** (直近 K ターン新しい主張なし)

2/3 成立で収束。`aufhebungTarget` は上限キャップとしてのみ残す。

結論生成には以下を渡す (現行の「直近 20 発話のみ」を廃止):

- 各 issue の Position 対と結論 (止揚 / 論破 / 結論なし + 理由)
- 未解決の事実問題 (RAG 解消失敗分) — **結論に明記** (誠実性)
- ラウンド/フェーズサマリ + レンズ別投票の集中度

## 7. ペーパーとの接続

- **論点分解 [0] はペーパーレビューゲートに前倒し**する。md 正本に `# 論点` 節を持ち、
  人間が Notion 風ブロック編集で論点そのものを調整・承認できる
  (詳細: [paper gate spec 変更](../../plan/20260702_respec_from_fable/09-paper-gate-debatability.md))。
- ペーパーは「出所が明示された薄い共通地盤」(出所ラベル + 仮説メカニクス分離 —
  [08](../../plan/20260702_respec_from_fable/08-paper-provenance.md))。証拠は Tension 単位の
  オンデマンド RAG で引く (ペーパーに厚く盛らない)。

## 8. 正直な限界 (spec として明記)

- 本エンジンは弁証法を「実装」するのではなく、**弁証法的な手続きを「強制」する**もの。
  真に創造的な第 3 案 (elevates の中身) が出るかは生成 LLM の能力依存で、構造が保証するのは
  「出たものが検証可能で、出所が追える」ことまで。
- **論点分解 [0] の粒度が全体の質の上限を決める**。3〜5 個クランプ + 人間レビューゲートで補う。
- 事実対立の RAG 解消は KG 材料の質に律速される。解消失敗は隠さず結論に明記する。
- 批准者が同一モデル系である限り甘受諾バイアスは残る (緩和は §5-4)。

## 9. 移行方針

- 新エンジンは `flow.engine = "dialectic" | "rounds"` の config スイッチで導入した。
  **2026-07-03 に既定を `dialectic` へ昇格** (PR-B 実装 + テスト green を受けたユーザ判断)。
  rounds エンジンはフォールバック用に無改変で併存する (`flow.engine=rounds` で戻せる)。
- コスト水準 (旧反定立): 1 issue あたり 8〜12 call (定立 2 + 反定立 ~4 + 分類 1 + 止揚 1〜2 + 批准 2〜4)、
  3〜4 issue で 30〜50 call。現行 (≈40 call) と同水準、判定系が小モデルに寄るぶん実コストは
  下がる余地がある。既存 `withCostLog` にそのまま乗せる。
- 論拠の応酬 (§2.6) 後は、論拠 n 件 (2〜6) × 応酬の段数ぶんの応答 + 反論ごとの前提ルール判定 + 再反論前の指名文が
  [2] に乗る (上限 `exchangeTurns` 既定 16)。反論が少なければ旧反定立と同程度、応酬が続けば増える。
