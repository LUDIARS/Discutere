# 代理戦争AI — 統合レビュー (実現可能性・実効性)

## 0. 結論

**総合判定: 条件付き成立 (両案一致)。**

- 人間の仮説「FT よりベクトル化データを食わせる方が高速で精度が高い」は、**「ベクトル」を数値のまま渡す意味では不成立**、
  **数値を材料にした言語化 + ジャンル別 design_gap + 本人発言の原文 + 主張と根拠の対応表 の束 (以下「人物パック」)** を
  in-context で渡す意味では **条件付き成立**。速度 (形成・更新) は成立、人物の再現と議論の質は評価で確かめるまで未立証。
- 人物ごとの FT は採らない (1 人の公開発言は数十件で学習量が 2 桁足りない。両案一致)。
- 形成と正本は **Histrio**、受け取って代理同士を議論させるのは **Di**。Voluptas は既存経路のまま独立 (両案一致)。
- 議論は既存 **dialectic に「代理モード」として載せる**。立場は index の pro/con 割当ではなく本人データから導く。
  本人根拠の無い主張は「推測」と区別し、論証の勝敗に効かせない (両案一致)。

一番の懸念 (両案の上位を統合):

1. **同一化**: 20D affect は同じジャンル好きの 2 人で近くなる。原文根拠に縛らないと数ターンで同じ意見に寄る。
2. **誤帰属**: 代理は本人が言っていないことを必ず言う。引用 / 根拠付き言い換え / 推測 / 不明 をデータで分け、露出面でも区別する。
3. **材料の薄さと評価漏洩**: ジャンル単位で gap を作れる話者数は未計測。形成と評価を原レビュー単位で分けないと評価が甘くなる。

## 2. 採用する方式

### 2.1 人物パック (Histrio → Di の契約、v1)

1 要素 = 1 話者 × 1 ジャンル。Fable §10 の JSON 案を土台に、Astra §10.3 の項目を足す。

- 識別: `contractVersion`, `personaKind=observedSpeaker`, `speakerKey` (`ext:<source>:<hmac16>`。生 ID・表示名を含めない。Di が形式検証)
- 版と来歴: `profileVersion`, 内容 hash, `generatedAt`, `expiresAt`, 形成方式 (`rule` / `llm`)、ルール・辞書版
- 範囲: `genre` (Histrio 辞書 id) + 辞書版、観測期間
- 充足度: 件数・正・負・ゲーム数・観点数・`confidence`・不適格理由
- 人物情報: `preferences` / `aversions` / `conditionalGaps[{current, desired, condition, evidenceIds}]` / `unknowns` / `conflicts`
- 補助: 20D affect と 20D gap (`method=pos-minus-neg`、作れなければ null + 理由)。prompt には出さない
- 立場カード: `{id, claim, polarity, evidenceIds[], extractor}`。根拠 ID の無いカードは出さない
- 根拠: `evidence[{id, revision, text(≤400字), sourceKind, gameTitle, polarity, postedAt?}]` (≤ 12 件。URL は U3 次第)
- 口調メモ: 頻度集計の 2〜3 行
- 評価用: `heldOut[{game, recommended}]` (本文は評価専用の別ファイル/別取得口。議論には載せない)
- 失効: `revoked`

### 2.2 Di 側の処理

```
取込 (契約検証・版固定・失効) → 束 (言語化・予算クランプ・議題で根拠並べ替え)
  → 代理キャスト (論点別に立場を判定。中立は opinion、欠員を架空人物で埋めない)
  → dialectic 代理モード (根拠 ID を引かせる / claimKind を返させる)
  → 帰属検査 (構造検査、障害時は不採用) → 表示 (「公開発言から作った AI の代理。本人の発言ではありません」)
```

- 既定 OFF (`flow.proxy.enabled=false`)。観点タグ「代理」が無ければ従来経路とバイト等価。
- Histrio 不通時は代理議論を始めない (通常の議論は影響なし)。
- 機密 / 内部タグでは代理モードを使わない (外部の声のゲートと同じ扱い)。

### 2.3 評価 (Di の `eval:proxy`)

- 評価用資料は原レビュー単位で分け、形成・検索・パックに入れない。
- 指標: 推薦予測 (多数派ベースラインとの差) / 観点別立場予測 / 判別テスト (blind) / 同一化の検出 / 根拠付き率 / 誤帰属率。
- 合格しないプロファイルは `eval_status=failed` で代理キャストから外す。予算 3.5k / 6k / 10k の比較もここで行う。

## 3. 実装の分割と受入条件 (統合)

| 段 | 場所 | 内容 | 受入条件 |
|---|---|---|---|
| S0 契約 | Di + Histrio spec | 契約 v1 の文書 + zod スキーマ + サンプル fixture | 表示名・生 ID・(U3 次第で) URL を含む行を拒否 / サンプルが全テストの fixture |
| S1 取込 | Di `src/flow/proxy/` | 検証・`flow_persona` (origin=histrio) upsert・プロファイル表 migration・失効・期限 | 再取込で行が増えない / revoked で archived / 期限切れはキャストに出ない |
| S2 束 | Di | 言語化・予算クランプ (既定 3.5k、上限 10k)・文区切り・議題での並べ替え | 出力が上限以下 / 数値が文字列に出ない / confidence=low は作らない |
| S3 議論接続 | Di dialectic | 立場判定・代理キャスト・根拠指示・`claimKind`・帰属検査・露出表記・入口 (タグ「代理」) | 中立は debater にならない / 根拠の無い反論は格下げ / 検査障害時に本人主張として採らない / 非代理議論は回帰なし |
| S4 評価 | Di `scripts/eval-proxy.ts` | 指標・ベースライン・judge キャッシュ・eval_status | モック LLM で決定的 / failed がキャストから外れる |
| S5 形成 | U1 次第 (Histrio または Di の仮置きスクリプト) | 話者 × ジャンル集計・数値 gap・根拠選抜・立場カード (決定的版)・held-out 分割・契約出力 | 同じ入力で同じ出力 / 正負不足は gap=null + 理由 / 根拠 ID の無いカードは出ない / 充足数レポート |
| S6 Histrio 基盤 | Histrio | 最小サービス (store・health・Excubitor 登録)・`GET /v1/personas?namespace=di` | Cc 停止時も単体で応答 / Di 側テストが契約サンプルのまま通る |

順序: S0 → S1・S2・S4 骨組み → S3 → S5 → S4 実測 (実 LLM、人間の許可後) → S6 (U1 で後回しを選んだ場合)。

## 4. 決定事項 (2026-10-23 neco「すべて推奨どおり」)

下表の「推奨」をそのまま採用した。

| # | 事項 | 推奨 | 理由 |
|---|---|---|---|
| U1 | **Histrio をいつ作るか** | **Di 側 (S0〜S4) を先に作り、形成は Di 内の仮置きスクリプトで契約ファイルを出す。Histrio のサービス化は契約が固まってから** | Histrio はコードが無く、サービス立ち上げ (Excubitor 登録・ポート・データ移行) が別に大きい。契約を先に固定すれば後で移すだけ。仮置きはスクリプトに留め、Di の常駐機能にしない |
| U2 | **Histrio の「LLM 不使用」を形成にも厳格に適用するか** | **初期は適用 (決定的抽出のみ)**。充足率と精度を測り、足りなければ LLM 抽出の例外を改めて判断 | 両案とも既定は決定的。LLM 抽出は Histrio の原則変更になる |
| U3 | **出典 URL を Di に渡すか** | **渡さない** (引用本文と revision は渡す。URL での監査は形成側で) | 1 人分の発言を束ねて出すと再特定しやすくなる。既存「出所は透明」の縮小なので人間が決める |
| U4 | **「10k」の意味** | **1 話者 × 1 ジャンルの上限 1 万トークン。既定は 3,500 で、評価で 3.5k / 6k / 10k を比べて決める** | 人間の数字を上限として守りつつ、同一化の懸念を測って解く |
| U5 | **対象範囲と名前** | **公開発言の仮名話者に限定** (Discord 利用者・実名の人・Cc の会話は材料にしない)。外部公開 (GLAB 等) はしない。露出名は「代理議論」 | 特定個人への攻撃に使える形にしない |

## 5. 片方にしか無い指摘の採否

- Fable のみ: 議題ごとの gap (採用) / 同陣営になっても反対へ回さない (採用) / 口調メモは頻度集計 (採用) / Histrio のロールモデルエンジンは代理議論では使わない (採用、Astra も「状況層は賛否を決めない」で同旨)。
- Astra のみ: 初期化コミットしかない Histrio を「既存サービスへの接続」と扱わない (採用、U1) / 由来ごとの正本・自動で同一人物を結合しない (採用) / 進行中の議論は人物パックの版を固定し、失効は版固定より優先 (採用) / 帰属検査の障害時に ok を返さない (採用) / 「高速」と呼ぶ条件 (品質基準を満たした方式同士で p95 が 80% 以下) (採用、評価レポートに入れる)。
