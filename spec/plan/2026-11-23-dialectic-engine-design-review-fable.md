# 議論エンジンの設計評価レビュー (fable)

## 総合評価: 3 / 5

**理由**: 「議論を発話の列ではなく論証の状態として持ち、遷移と決着をコードが決める」という中心の判断は正しく、
結論なしを正当な出力にした点も良い。一方で、(a) 論拠が崩れるかどうかが論証の中身ではなく
「打ち切り」と「本人が認めるか」で決まる、(b) 根拠の出所が通常の議論では型付け・検査されない、
(c) 作り手が次の手を決めるための出力の形が設計されていない、(d) 議論の質を測る仕組みが無い、の 4 点が
目的に対して足りない。v2 改善設計は記録と結論の不一致を正しく直すが、(a) と (d) には届いていない。

### 議論エンジンの目的 (自分の言葉で)

ゲームの仕様や体験についての問いを、検証できる小さな命題に分け、プレイヤーの声とゲームの資料を根拠にした
賛否の論拠を出させて、**どの論拠が残り、どれが崩れ、何が今ある材料では決められないか**を記録に残す。
作り手はその記録から「条件付きでこう直すとよい」「これは決められない。決めるにはこの材料が要る」を読み取り、
次の手 (試す・測る・保留する) を決める。面白い統合案が出ることは副産物で、保証するのは
出た結論の出所と決着の経緯が追えることである。

読んだもの: 依頼書の「読むもの」全部。実装は `native/src/flow/dialectic/` の
`driver.cpp` / `convergence.cpp` / `goal.cpp` / `outcome.cpp` / `conclusion.cpp` / `ground_state.hpp` /
`position.cpp` / `turn_prompt.cpp` / `exchange_prompt.cpp` を裏取りに使った。
他のレビュー出力と `2026-11-23-dialectic-v2-implementation-plan.md` は読んでいない。
議論・ビルド・テスト・LLM の実行はしていない。

## 1. 目的との適合

### 1-1. 論証モデルの土台は目的に合っている (良い判断)

主張・データ・論拠・限定を分け、根拠ごとに状態を持つ (`dialectic.md` §1, §2.5) ので、
「どの根拠が残ったか」を記録から機械的に言える。旧 rounds エンジンの「要約 → 雰囲気で止揚判定」
(`dialectic.md` §0) に比べ、作り手が結論を疑って遡れる点で明確に良い。
限定 (どの層・どの条件の話か) を主張の必須要素にしたのは、ゲームの改善が
ほぼ常に「誰にとって」の話であることに合っている。

### 1-2. 【重大】「成り立つ反論」に中身の審査が無く、応酬が自然に終わらない

- `dialectic.md` §2.6 の決着は「成り立った反論が 1 つでもあれば崩れる」。反論が「成り立つ」条件は、
  形 (データと論拠がある、突く要素を宣言) と前提ルール違反でないこと (§2.5) だけで、
  **その反論が相手の論拠を実際に崩しているか**は誰も審査しない。
- LLM は形の整った反論をいくらでも書けるので、連鎖は「本人が認める」か上限でしか止まらない。
  `2026-10-13-dialectic-v2-improvement.md` §0・P2 の実測がこれを示している
  (#144 は 3 論点とも上限 16 で打ち切り、連鎖で崩れた論拠は 13 件中 0 件、崩れたのは「認める」3 件だけ)。
- つまり現設計で論点の結論を決めているのは、論証の強さではなく (i) 上限の位置と (ii) どのモデル・人物が
  認めやすいか、である。論破 (`goal.cpp:20-38` — 立っている根拠が 0 の側が負け) も同じ入力に乗る。
- v2 の `unsettled` (P2) は「打ち切りを勝ちにしない」ので正直にはなるが、終わらない応酬そのものは残る。
  推測: v2 では大半の根拠が未決になり、ほとんどの論点が「結論なし (未決)」になる。

→ 観点 8 の代替案 A (応酬は固定 2 手、決着は論拠ごとの独立審査) を勧める。

### 1-3. 【重大】出力が「討論の勝敗ラベル」で、作り手の次の手になっていない

- 論点の結論は 止揚 / 論破 / 結論なし の 3 区分 (`dialectic.md` §4.5)。これは討論の決着の分類で、
  作り手が欲しい「何を・誰向けに・どの条件で変えるとよいか」「何を測れば決まるか」ではない。
- 結論なしは今後も多数派になる見込みで (`v2-improvement.md` §6 の参考表は 3 論点とも結論なし寄り)、
  そのときの価値は「決着に要る材料」にある。v2 は「何が足りないかを結論に明記するところまで」(§6 末尾) と書くが、
  それを載せるデータの置き場 (論点ごとの「決着に要る材料」の一覧) が設計に無く、結論生成 LLM の文章頼みになる。
- 「論破」は作り手には「その主張は誤り」と読めるが、実際の意味は
  「その人物が出した 1〜3 件の論拠が残らなかった」である。主張の真偽ではなく論拠の出来を測っている。
- 事実対立を照会で解消できても区分は「結論なし」(§4.5)。確かめられた事実は成果なのに、
  最も弱いラベルに入る。v2 P5 は文面を分けるだけで区分は変えない。

→ 論点ごとの出力を「決着カード」にする: 残った論拠 (条件付き) / 崩れた論拠 / 未決 / 確かめられた事実 /
決着に要る材料 / 未検証の提案 (止揚)。3 区分は見出しとして残してよい。

### 1-4. 【注意】賛成・反対の二値は「探る」型の問いに合わない

- 定立は「賛成 = 問いに はい / 反対 = いいえ」(`dialectic.md` §2.7、`position.cpp:35-36`)。
  ところが実際の議題は「長寿コンテンツとして遊ばれ続ける理由を探る」(`v2-improvement.md` 冒頭) のような
  説明を求める問いで、論点 ①「メカニクスの十分な面白さ」は はい/いいえ に落とした時点で
  「メカニクス」の範囲のずれ (P5) を生んだ。
- 改善を考える議論で役に立つのは多くの場合「A か B か」より「どの層に・どの条件で」である。
  二値で争わせた後に止揚で条件分割に戻すのは遠回りで、応酬のトークンの多くが定義のずれに使われる。

### 1-5. 【注意】「共通見解の前提」を置く場所が無い

`dialectic.md` §2.5 は「どんな体験をつくりたいか・どんな施策を試したいか・他のゲームではどうか」は
共通見解が取れている前提とするが、ペーパーの節は 議題 / 観点補足 / メカニクス / 論点
(`OVERVIEW.md` §5.1) で、「つくりたい体験」を書く節が無い。書かれていない前提は各 LLM が各自で補うので、
価値対立の多くが「目標体験の解釈違い」になる。ペーパーに `# つくりたい体験` (人が書く・無ければ
「未指定」と明記) を持たせるべき。

## 2. 役割と進行の構造

### 2-1. 【重大】立場が人物像と無関係に割り当てられる

- 賛否は debater を均等割りで固定する (`20260702_respec_from_fable/01-persona-state.md` §1)。
  固定そのものは正しい (毎ターン抽選より一貫する)。
- ただし割り当てが人物の価値軸・遊び手の型と独立なので、「探索を重んじる人」が探索を削る案の賛成役に
  なり得る。アーキタイプ設計案も「型は立場を変えない」(`persona-game-archetype-context.md` §2.2) と明記する。
  この場合 LLM は人物像を無視するか、立場を見失う (#142 で起きた「自陣営と逆向きの反論」と同じ形)。
- 代理議論は正しい形を既に持っている: 「立場は論点ごとに本人のデータから決める。分かれなければ反対役を作らず
  結論なし」(`proxy-debate.md` §2)。通常の議論もこれに揃え、**立場は論点ごとに人物像から導く**
  (分かれなければ「この顔ぶれでは対立しない」と記録するか、別の型の人物を足す) のが筋である。

### 2-2. 【注意】意見役と投票者の役割が dialectic では宙に浮いている

- `OVERVIEW.md` §4・§5.2 は 進行役 / 賛成 / 反対 / 意見役 を定義し、意見役だけにユーザーの声を渡す。
  `dialectic.md` の位相 [1]〜[4] に意見役の手番は無い。
- `OVERVIEW.md` §6 は「賛成派・反対派 (クラウド LLM) は RAG 不許可」だが、`dialectic.md` §2.7 と v2 P9 は
  賛否役に声 (V 番号) をデータとして引かせる。声を持つべきなのは論拠を立てる当事者なので、後者が正しい。
  OVERVIEW の表を直すべき (旧設計の名残)。
- 同種の名残: `OVERVIEW.md` §4「賛否は固定せずターン時に決定する」(§1 と矛盾)、
  `discussion.md` 冒頭「rounds エンジン (既定)」(`dialectic.md` §9 は dialectic が既定)、
  `dialectic.md` §5「判定は Haiku 級」(`model-roster.md` §3 は Sonnet / Fable)。【軽微】だが、
  正本が複数の時点を混ぜて語るので、設計の現在形を読み取りにくい。dialectic が既定になった以上、
  OVERVIEW の役割・RAG 表は dialectic を基準に書き直すのがよい。

### 2-3. 【重大】論点の形を、応酬の前に確かめていない

- `dialectic.md` §8 自身が「論点分解の粒度が全体の質の上限を決める」と書く。人間の承認ゲート (§7) は良い。
- しかし論点に求める形 (1 つの命題か・用語の範囲が決まっているか・何をもって はい と言うか) の検査が無い。
  v2 P5 は「定義のずれ」を対立の型として**応酬の後**に検出するが、その時点で応酬 16 ターンは使い終わっている。
- 対立の型分類 (位相 [3]) も応酬の後にある。事実対立は「弁証法のスコープから外す」(§2) はずなのに、
  先に弁舌で争わせ、しかも「論破は事実照会より前に判定する」(§4.5) ので、事実の問題が照会されないまま
  勝敗が付き得る。

→ 論点を「命題 + 用語の定義 + 判定基準」の組にしてペーパーゲートで確定し、定立の直後 (応酬の前) に
型を判定する。定義のずれは人に聞く、事実は先に照会する、価値・手段・トレードオフだけ応酬に進める。

### 2-4. 【注意】セッション単位の収束判定に根拠が無い

- 収束は (a) 未応答反論 0 / (b) 投票集中 / (c) 新規主張の枯渇 の 2/3 (`dialectic.md` §6、`convergence.cpp:7-15`)。
  論点は独立に回る (§3) ので、論点 1 の投票が集中したことは論点 2 を議論しなくてよい理由にならない。
- (a) は応酬が落ち着けば論点の決着時点でほぼ成立する (推測: `driver.cpp:693-712` の評価位置から)。
  すると残り 1 条件で LLM 分解の残り論点が打ち切られる。#142 で論点 2・3 が打ち切られたのは
  この構造の帰結で、「人が指定した論点は打ち切らない」(§6) は症状への対処である。
- 論点を独立にするなら、打ち切る基準は予算 (呼び出し数・時間) だけにし、
  「収束」の語は論点の中の決着に限るのが分かりやすい。

### 2-5. 幅優先・発言数最少の応答者選び

幅優先 (§2.6) は公平で良い。応答者を「発言数最少」で選ぶと連鎖の途中で論旨が乗り換わる点は
v2 P6 (元の反論者を優先) で直る。妥当。

## 3. 評価・判定の仕組み

| 仕組み | 保証しようとしていること | 見合うか | 所見 |
|---|---|---|---|
| 投票 (レンズ別) | 世論 = その論点の主要意見、収束シグナル (b) | **見合わない** | 下記 3-1 |
| 前提ルール判定 | 反論が相手の限定の内側を突いている | 概ね見合う | 下記 3-2 |
| 「認める」の検証・立場の向き | 発言種別と陣営の誤りを防ぐ | 見合う | 生成の失敗への継ぎ当てだが安い |
| 型分類 | 型に応じた解法へ振る | 位置が悪い | 2-3 のとおり応酬の前へ |
| 折衷ゲート | 「両方やる」を止揚と呼ばない | 見合う | 安く、空洞化を防ぐ。残す |
| 批准 | 両陣営の根拠の過半を保存 | 部分的 | 下記 3-3 |
| 事実照会 | 事実の対立を証拠で解く | 部分的 | 下記 3-4 |

### 3-1. 【注意】投票は dialectic では役割を失っている

- 投票の候補はその論点の全発話 (進行役とエラー以外) で、格下げされた発話も崩れた論拠も含む
  (`driver.cpp:656-658`)。選ばれた「世論」は論点の決着に影響せず、収束シグナルと結論生成の入力
  (`conclusion.cpp:82-98`) にだけ使われる。
- 状態機械が決着を持つエンジンで「一番良い発話」を選ぶ意味は薄く、むしろ崩れた論拠が
  「世論」として結論生成に渡り、v2 P3 が防ごうとしている「崩れた論拠の復活」の経路になり得る。
- 投票者 N 回ぶんの呼び出しは、1-2 の「論拠ごとの独立審査」に付け替えるのが良い
  (レンズ別・提示順シャッフルという `03-vote-lenses.md` の工夫はそのまま審査に使える)。

### 3-2. 【注意】判定 LLM が障害時に通す側へ倒れる・ラベルが増え続けている

- `dialectic.md` §2.5 ゲート 2「障害・ラベル不明は ok に倒す」。ok になった反論は有効な論拠として数えられ、
  相手の根拠を崩し得る。代理議論は「検査できない状態を ok にしない」(`proxy-debate.md` §3)。
  同じエンジンの中で方針が逆である。検査できなかった反論は「未決」に落とすのが揃った扱い。
- 単一ラベルの判定に載る違反が `out_of_scope` / `straw_man` / `dismissal` / `topic_shift` /
  `self_contradiction` (§2.7) と増え、v2 P8 でさらに `mechanic_mismatch` が足される。
  1 回の呼び出しで 6 種を単一ラベルで判定させる精度は測られていない (観点 6)。
  また P8 は反論だけを見るが、仕組みと矛盾する前提は定立の論拠で最初に入る (#142 の例は定立)。
  メカニクスとの照合は定立の検査として別に置く方が効く。

### 3-3. 【重大】止揚は「未検証の新しい主張」なのに最上位の結論として扱われる

- 批准が保証するのは「各陣営の根拠の過半が ID で保存されている」こと (`dialectic.md` §5-2)。
  止揚の中身、特に `elevates` (新しい枠) は、応酬を一度も通っていない新しい主張である。
- 定立の論拠は反論に晒されるのに、止揚案は晒されない。それでいて「◎ 最も止揚らしい」(§2) と
  最上位の成果に位置づけられ、#144 では撤回済みの推論を中心に据えた止揚や判定基準のすり替えが通った
  (`v2-improvement.md` P3)。v2 は批准の質問を増やして対処するが、批准者は「自分の根拠が残ったか」を見る役で、
  新しい枠の妥当性を見る役ではない。
- 止揚は「提案 (未検証)」として出し、その前提 (どの残った論拠に依るか・新たに仮定したこと) を列挙させるか、
  1 回だけ反論に晒すべき。

### 3-4. 【注意】事実照会が 1 経路しかない

事実対立は KG の外部の声で照会する (`06-dialectic-core.md` [3])。声で確かめられるのは
「プレイヤーがどう感じ、どう語っているか」で、「売上が下がるか」(§2 の表の例) は確かめられない。
事実は少なくとも 3 種に分けられる: ゲームの仕様 (ペーパーのメカニクス表で確かめる) /
プレイヤーの受け止め (声の件数と内訳で確かめる) / 行動・数値 (Di には無い。常に「未解決 + 要る材料」)。
型を分ければ、照会しても決まらない問いに LLM 判定を使わずに済み、「要る材料」も正確に書ける。

### 3-5. トークンの使い方

- 論点 1 つの上限 (推測。`dialectic.md` §9 と §2.6・§2.7 の足し上げ): 定立 2 + 向き判定 2 +
  応酬 16 + 前提ルール判定 16 + 「認める」検証・指名文 数回 + 型分類 1 + 事実照会 1 +
  止揚 1〜3 + 折衷ゲート 1〜3 + 批准 2〜6 + 投票 N。50 回前後になり、3 論点で 150 回規模。
- その 6 割以上が応酬と応酬の判定で、#144 ではそこから連鎖で崩れた論拠が 0 件だった。
  **最も費用を使う部分が、決着への寄与が最も小さい**。費用対効果の面からも 1-2 の見直しが要る。
- 役割ごとのモデル分け (`model-roster.md` §5: 頻度の高い判定は Sonnet、最終採否だけ Fable) は妥当。
  Codex 経路の失敗を Claude に代弁させない (§6) も良い判断。

## 4. 人物像と文脈

### 4-1. 現状: 賛否役の人物像は飾りに近い

dialectic の発話・定立 prompt に載るのは 名前・特徴・話し方・価値軸 だけ
(`turn_prompt.cpp:62-63`、`exchange_prompt.cpp:57-58`、`position.cpp:27-36`)。価値軸はセッション開始時に
LLM がテーマから作る (`01-persona-state.md` §2)。プールの人物 (遊び手の型の軸・苦手) は
dialectic の prompt に届かない (`persona-game-archetype-context.md` §1 の調査と一致。
`driver.cpp:229` は憑依名を表示に使うだけ)。アーキタイプ設計案の問題認識は正しい。

### 4-2. 人物像の効かせ方 — 立場ではなく「限定」と「論拠の重み」に

- 人物像は「誰にとっての話か」を持ち込むために使うのが、この論証モデルと最も噛み合う。
  人物の型を主張の限定 (層・条件) に結びつけ、「この型の遊び手にとっては」という条件付きの論拠を出させる。
  そうすれば型の違いは、立場の言い合いではなく条件分割 (価値対立の解法、`dialectic.md` §2) の材料になる。
- 立場は 2-1 のとおり人物像から導く。

### 4-3. 【重大】人物の「感じ方」がプレイヤーの声と同格のデータになる危険

設計案は「この型の人として、論点についてどう感じるかを根拠と一緒に言う」(§2.1) とする。
型から推した感じ方は合成であり、実際の声ではない。通常の議論には発言の出所を区別する仕組みが無い
(観点 5) ので、「私のような遊び手は離脱する」がデータとして論拠に入る。代理議論は型からの推測を
混ぜないために対象外にされている (§2.3) が、通常の議論こそ同じ区別 (`claimKind` の推測) が要る。
A1 を入れる前提として、観点 5 の出所の型付けを先に入れるべき。

### 4-4. 【注意】人生脚本パターンの使いどころ

- Histrio の仕様では脚本パターンは**立場ベクトルの主因**で、「論者間の立場ベクトルの差がそのまま
  討論の対立軸になる」(`virtual-persona-life-script.md` §3, §5)。Di は立場をセッションで固定し、
  設計案は「立場には効かせない」方向で使う (§2.1 の人物像ブロック)。2 つの設計の前提が食い違っている。
- 脚本パターン (`until` = 条件が揃うまで保留、`never` = 現状維持へ寄る など、同 §2.1) は
  決定や進め方への態度で、ゲームの好みではない。Di の応酬で態度が効く箇所は「反論するか・認めるか」であり、
  1-2 のとおりそこが決着を左右する。つまり脚本パターンを載せると、**性格が勝敗を決める**。
- 勧め: 脚本パターンは口調にだけ使い、認める・反論の選択には使わせない。A3 は効果が測れてから。

### 4-5. 人物像の正本を Histrio に置く方針

- 責務の分け方 (Voluptas = 本人の同意済みデータ、Histrio = 公開発言由来の人物像、Di = 受け取って議論。
  `proxy-debate.md` §6、`persona-pool.md`) は筋が通っている。Di が人物を生成しない原則は残すべき。
- 懸念: 人物像の正本が種類ごとに 3 か所 (Voluptas の匿名ペルソナ / Di のプール = 公開レビュー話者の採用 /
  Histrio の仮想人格と人物パック) になり、設計案はさらに 1 人の人物を「遊び手の型は Di、脚本は Histrio」に
  割る (`persona-game-archetype-context.md` §2.3)。Histrio はコードが無い (同 §1)。
  D2 の推奨 (A1・A2 を先に、Histrio は別タスク) に賛成。Di は「言語化された人物像 + 軸 + 出所」を受け取る
  契約だけを決め、Histrio が無くても同じ質で動くことを条件にする。

### 4-6. 【注意】ゲームの型の正本 (D1)

- Ludus の 17 ジャンル (`Ludus/spec/data/game-template/README.md` §0) は実装テンプレート
  (コード設計・必須機能が中心) で、買い切りのアクション・RPG・パズル等が対象。運営型・ガチャ・協力マルチの
  スマホゲームに当たるジャンルが無い。レビューの題材になっているモンスターストライクは 17 のどれにも
  素直に当たらない (推測: 各ジャンルの INDEX は未読)。「当たらないときはブロック無し」(設計案 §3 A2) なので、
  今いちばん議論している種類のゲームで効かない。D1 は「はい」でよいが、Ludus 側のジャンル追加か、
  ペーパーで人が型を書ける経路を主にする必要がある。
- ジャンルの「遊び手が期待する体験」は一般論である。system に置くのは良いが、
  論拠のデータ (帰納) として数えさせない (出所: ジャンルの型・一般論、と明示する)。

## 5. 根拠の扱い

### 5-1. 【重大】通常の議論では根拠の出所が型付けされず、コードで検査されない

- `Ground.kind` (演繹 / 帰納 / アブダクション、`dialectic.md` §2.5) は推論の種類で、出所の種類ではない。
  データ (`text`) は自由文で、声を引いたのか・資料を引いたのか・一般知識なのか・推測なのかを区別しない。
- 代理議論には正しい仕組みが既にある: 論拠ごとに 引用 / 言い換え / 推測 / 不明 を申告させ、
  引いた番号が束にあること・引用が原文に含まれることをコードで確かめ、通らなければ推測に落とす
  (`proxy-debate.md` §3)。これが通常の議論に無いのは設計の非対称である。
- 「帰納 = 他のゲームではこうだった」は、ペーパーにも KG にも無ければ LLM の一般知識で、検証できない。
  現設計ではこれがデータとして通る。
- v2 P4 (声の固定番号・一覧) は検証の前提を作り、P9 は「データなしの演繹」を区別するが、
  番号の実在と引用の一致を確かめる検査は入っていない。

→ 全議論で、論拠のデータに出所 (声 `V..` / メカニクス `M..` / ペーパー本文 / 推測) を持たせ、
番号の実在と引用の一致をコードで検査する。出所の無い論拠は「推測」として数え、集計と結論で分ける。

### 5-2. 【重大】崩れた論拠・未決の命題が結論に入るのを止める仕組みが文章頼み

- 現状、結論は決着表の要約と全発話を渡して LLM が自由に書く (`conclusion.cpp:79-103`)。
  崩れた論拠も全発話に含まれるので、復活を止めるものが無い (#144 で実際に起きた)。
- v2 P3 は (i) 止揚の入力から崩れた根拠を外す、(ii) 決着表をそのまま本文に写す、(iii) 指示を足す、
  (iv) 判定 LLM で矛盾を検出して 1 回作り直す。方向は正しい。ただし (iii)(iv) は LLM の遵守と
  LLM の検出に頼る。
- より確実な形: 結論の各文に、依る論拠の ID を付けさせ、**ID が「残った」集合に含まれることをコードで確かめる**
  (含まれなければその文を落とすか作り直す)。止揚の `preserves[]` を折衷ゲートで見る P3 の考えを、
  結論本文にも同じ形で適用する。

### 5-3. 【注意】声の偏りと、議論の成果の学習データ化

- 声は続けている人に偏る (`dialectic.md` §2.7 の表、v2 P9)。P9 の「内訳を一言載せる」は良い。
  ペーパーゲートの証拠バランス検査 (`09-paper-gate-debatability.md` §1) はペーパー単位で、論点単位ではない。
  論点ごとに引いた声の内訳を決着カードに載せ、片側しか無い論点は「片側の声しか無い」を結論なしの理由にできる。
- `OVERVIEW.md` §7「すべての議論の発話・結論は次の議論の学習データになる」。AI の発話が KG に入り、
  後の議論で外部の声と同じ検索に乗るなら、合成の意見がプレイヤーの声として戻ってくる。
  機密の想定意見には「合成と明示」(§5.4) があるのに、議論の発話にはその記述が無い。
  (推測: 検索側で出所を分けているかは未確認。設計書には分離が書かれていない。)

### 5-4. 良い判断

ペーパーの出所ラベルと仮説メカニクスの節分離 (`08-paper-provenance.md`)、議論フローでは LLM 増補をしない
(`discussion.md` §2-0)、`機密`/`内部` では蓄積済みの声も引かない (`OVERVIEW.md` §3)、
未解決の事実問題を結論に必ず書く (`dialectic.md` §6) は、いずれも根拠の扱いとして正しい。

## 6. 測り方

### 6-1. 【重大】議論の質を測る設計が無い

- 今ある測定: コストと transcript の記録 (`OVERVIEW.md` §8)、代理の本人らしさの評価
  (`proxy-debate.md` §5)、検索精度の評価 (CLAUDE.md の `eval:retrieval`)。
  議論エンジン本体の質については、**1 つの議題を 1 回流し、LLM レビュー 2 件が 5 段階で採点する**
  (`v2-improvement.md` §1 の 5・§5) だけである。
- 問題: (i) 同じ議題でも LLM の出力は実行ごとに変わるので、v1 と v2 を 1 回ずつ比べても
  改善とばらつきを分けられない。(ii) 議題が 1 つ。(iii) 採点者が生成側と同系統のモデルで、
  基準が版ごとに揃わない。(iv) v2 は「v1 の挙動に戻すフラグは持たない」(P10) ので、
  同じコードでの対照実験ができない。
- 代理議論の評価は良い手本である: 伏せた材料・基準線との比較・合格の閾値・「分からない」を正解に数えない。

### 6-2. 置くべき測定 (設計として)

| 層 | 測るもの | 方法 |
|---|---|---|
| 記録の整合 (毎回・コードのみ) | 結論が引く論拠 ID がすべて「残った」/ 全論点が結論に載る / 集計が状態と一致 / 声の番号が本文に解決できる / 打ち切りが明示されている | 議論の終わりに検査レポートを自動で出す。v2 §1 の受入 1・3・4 はこれで機械判定にできる |
| 決着の妥当性 (版ごと) | 固定の議題セット (5〜10 件) での区分の一致率 | 人が「妥当な結論」を先に書く (`v2-improvement.md` §6 の表が 1 件目)。仕込み入りの議題を混ぜる: 声で答えが出る事実 / 定義がずれる論点 / 片側の声しか無い / 仕組みと矛盾する前提 |
| 安定性 | 同じペーパーを k 回 (3 回) 流したときの区分の一致率 | 一致しない論点は「決着が偶然に依る」ことの直接の指標 |
| 判定 LLM の精度 | 前提ルール・「認める」検証・折衷ゲート・批准の正解率 | 過去の記録から人がラベルを付けた小さなセット (各 30〜50 件) で適合率と再現率 |
| 費用 | 論点あたりの呼び出し数・決着した論拠 1 件あたりの費用 | 既存のコストログの集計 |
| 役に立ったか | 作り手が決着カードの項目に付ける「使えた / 使えない」 | 学習ビューに 1 操作で付けられるようにする。目的に対する唯一の直接の指標 |

版の記録 (P10) に加え、セッションごとに設定の写し (モデル編成・上限・判定の有無) を残す
(モデル編成が結果を変えるため、版だけでは比較できない)。

### 6-3. 測れない部分 (正直に)

止揚の新しい枠が本当に創造的か。Di に無いデータ (継続率・売上) に依る主張の真偽。
結論を読んだ作り手の判断が良くなったか (「使えた」の印は代理指標でしかない)。
人物像が実在の遊び手の反応をどれだけ写しているか (代理議論の判別評価を型の人物にも流用すれば
「人物ごとに発言が区別できるか」までは測れる)。

## 8. 代わりの設計

### 案 A: 論点ごとの独立した小議論 + 論拠の独立審査 (勧める)

```
[0] 論点 = 命題 + 用語の定義 + 判定基準 (人が承認)
[1] 定立 (賛否。出所を型付けした論拠 1〜3 件。番号・引用・メカニクスとの整合をコードで検査)
[2] 型の判定 → 定義のずれ: 人に聞く / 事実: 種類別に照会 / それ以外: [3] へ
[3] 応酬は固定 2 手 (各論拠に反論 1 件 → 持ち主の応答 1 件)。論点内で並列に回せる
[4] 論拠ごとの審査: 独立の審査役 (レンズ別・提示順シャッフル、今の投票の枠) が
    「残る / 弱まった / 崩れた」と理由を出し、多数で決める (割れたら未決)
[5] 決着はコードが集計。止揚は任意の「提案 (未検証)」として前提付きで添える
[6] 出力 = 決着カード (1-3)
```

| | 今の設計 (+ v2) | 案 A |
|---|---|---|
| 論拠が崩れる条件 | 形の整った反論に答えられない・本人が認める・上限 | 審査役の多数が「崩れた」と判断 |
| 最後の一手の偏り | 未決にして中立化 (v2) | 構造上生じない |
| 呼び出し数 (論点あたり) | 上限 50 前後・応酬次第で変動 | ほぼ固定 (定立 2 + 応酬 ≤12 + 審査 論拠数 × 審査役) |
| 結果の安定性 | 認めるかどうかに依る | 審査の多数決で安定しやすい (推測。6-2 の安定性で確かめる) |
| 失うもの | — | 深い連鎖から出る論点 (#144 では寄与が小さい)。審査役が同系統モデルなら同調の偏りは残る |
| 見世物としての面白さ | 応酬が長く続く | 短くなる。Di は「遊びの議論」でもあるので、露出の文体・指名文は今のまま保つ |

今の実装から段階的に移れる: `argumentDepth` を 2 に下げる → 投票を論拠の審査に付け替える →
型判定を定立の直後へ移す。状態・永続・露出はそのまま使える。書き直しは要らない。

### 案 B: 声の集計を先に置く (案 A の前段として)

論点ごとに、引いた声を立場と層で分けて件数を出し (分類は小さい判定 LLM、集計はコード)、
「証拠の地図」を賛否役に渡す。声が割れている所だけを争わせ、片側しか無い所は「片側の声しか無い」と
先に記録する。プレイヤーの声を根拠にするという目的に最も直接的。ただし企画段階の新作や `機密` では
声が無いので、これだけでは回らない。単独の置き換えではなく、案 A の [1] の前に置く材料として使う。

### 案 C: 人間の介入点を「決められない所」に置く

今の介入点は開始前のペーパーゲートと進行役への調整指示 (CLAUDE.md) だけ。エンジンが持たず人が持つものは
(i) 用語の意味と (ii) 手元の数値 (継続率など) である。型判定で「定義のずれ」「行動・数値の事実」に当たった
論点だけ、スレッドに 1 問で聞く (「メカニクスに協力プレイを含めますか」「更新のある月と無い月の
アクティブ率の差は分かりますか」)。時間切れなら未決のまま進める (議論を止めない原則を守る)。
最も安く質が上がる変更で、案 A・今の設計のどちらにも足せる。

## 設計として直すべきこと (上位 5 件)

1. **【重大】論拠の決着方式** — 「形の整った反論が残れば崩れる」をやめ、応酬を固定の手数にして
   論拠ごとの独立審査で決める。投票はその審査に付け替える (1-2, 3-1, 案 A)。
2. **【重大】根拠の出所の型付けとコード検査を全議論に** — 代理議論の `claimKind` と引用検査を一般化し、
   声・メカニクス・推測を区別する。結論の各文は残った論拠の ID だけを引けることをコードで確かめる (5-1, 5-2, 4-3)。
3. **【重大】論点の形と型判定の前倒し** — 論点を「命題 + 用語の定義 + 判定基準」にしてゲートで確定し、
   型を応酬の前に判定する。定義と手元の数値は人に 1 問で聞く (2-3, 3-4, 案 C)。
4. **【重大】作り手向けの出力の形** — 論点ごとの決着カード (残った論拠・条件 / 崩れた論拠 / 未決 /
   確かめられた事実 / 決着に要る材料 / 未検証の提案)。止揚は未検証の提案として扱う。
   ペーパーに「つくりたい体験」の節を置く (1-3, 1-5, 3-3)。
5. **【重大】測定の仕組み** — 記録の整合の自動検査、仕込み入りの固定議題セット、複数回実行の一致率、
   判定 LLM の精度、作り手の「使えた」の印。v2 の受入をこれに置き換える (6)。

次点: 立場を論点ごとに人物像から導く (2-1)。判定の障害時は通さず未決にする (3-2)。
セッション単位の収束判定をやめ、予算で打ち切る (2-4)。OVERVIEW の役割・RAG の表を dialectic 基準に直す (2-2)。

## 残すべき良い判断

- 議論を論証の状態として持ち、遷移・進行・決着をコードが決める (`dialectic.md` §0, §3)。
- 生成と判定を別の呼び出しにする。批准は否定する動機を持つ側に reject 既定で聞く (§5)。
- 結論なしを正当な出力にし、合意判定を撤去した。双方崩壊は勝敗を付けない (§4.5)。
- 折衷ゲートで「両方やる」を止揚と数えない (§4)。
- 未解決の事実問題を結論に必ず書く。「正直な限界」を仕様に書く (§6, §8)。
- 人が承認した論点は打ち切らない。論点分解を人間のゲートに前倒しする (§6, §7)。
- ペーパーは出所を明示した薄い共通地盤。仮説メカニクスを分ける。議論フローでは LLM 増補をしない
  (`OVERVIEW.md` §5.1、`08-paper-provenance.md`、`discussion.md` §2-0)。
- 議論適性ゲートと別フローの再提案 (`09-paper-gate-debatability.md`)。
- `機密`/`内部` の扱いと、合成意見の明示 (`OVERVIEW.md` §3, §5.4)。
- 代理議論の帰属検査 (検査できないものを通さない)・判別による評価・推薦予測を実測で必須から外した判断
  (`proxy-debate.md` §3, §5)。
- Di は人物を生成せず契約で受け取る責務境界 (`persona-pool.md`、`proxy-debate.md` §6)。
- 役割ごとのモデル分けと、Codex 経路の失敗を Claude に代弁させない (`model-roster.md` §5, §6)。
- 全 LLM 呼び出しのコスト・transcript 記録と、失敗を議論の場に見せる方針 (`OVERVIEW.md` §8, §10)。
- 投稿の見た目を変えずに内側の構造だけを変える (`dialectic.md` §2.6) — 遊びとしての議論を保っている。
