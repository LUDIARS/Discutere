# C++ 版サーバの非同期化 (イベントスレッド + コルーチン) 設計 (2026-11-10)

> 状態: 設計 (未着手)。対象: `native/src/` 全体の並行性の持ち方。
> 経緯: C++ 版の運用レビューで「スレッド間で共有する状態を mutex で守る」構造が検査なしで広がっていることが
> 分かり、共有状態の持ち主を 1 本のスレッドに寄せ、待ちは非同期にする方針にした。

## 1. 目的と、目的にしないもの

- **目的**: データ競合とロック順の誤りを、検査で見つけるものから構造上起きないものにする。
  Node 版が持っていた「状態を触るのは 1 本だけ」という性質を取り戻す。
- **目的**: 中断・期限・終了処理を素直に書けるようにする (今は終了時に 20 秒の監視タイマーと `std::_Exit`)。
- **目的にしない**: 速度とメモリ。同時に進む議論は数本で、LLM は `claude -p` の子プロセスなので、
  待っているスレッドのコストは誤差。

## 2. 現状 (2026-11-10 計測)

| 項目 | 値 |
|---|---|
| `std::mutex` の宣言 | 90 箇所 / 14 モジュール |
| 起動直後のスレッド数 | 29 (HTTP の I/O 2 + ハンドラ用プール + 背景プール 8 + タイマー 1 + ほか) |
| 背景ジョブへの投函・タイマー登録 | 約 60 箇所 |
| `detach()` | 8 箇所 |
| TSan (全 202 テスト) | 実際の競合 1 件 (`PeriodicTask`、修正済み)。ロック順の逆転 3 件はテストが DB を作り直すため |

TSan の検出が少ないのは安全だからではない。テストの大半は 1 モジュールを単体で動かし、議論の進行中に
Discord のイベントや HTTP が重なる状況を作っていない。

今の決まり (`native/docs/PORTING.md`「非同期 → 同期」) は、TS の `async` を同期関数にし、LLM・HTTP・子プロセスの
待ちを呼んだスレッドで行う。理由は資料に残っていない。

## 3. 目標の構造

```
            ┌──────────────── イベントスレッド (1 本) ────────────────┐
 Discord WS │  イベントの振り分け / セッションと進行中議論の表 /        │
 Slack WS  ─┤  議論の進行 (コルーチン) / タイマー / HTTP ハンドラ       │
 HTTP      ─┤  ── 共有状態を読む・書くのはここだけ ──                  │
            └───────┬──────────────────────────────▲──────────────────┘
                    │ co_await (待ちを手放す)        │ 完了を投函
            ┌───────▼──────────────────────────────┴──────────────────┐
            │ 非同期 I/O: LLM (`claude -p`)・外部 HTTP・子プロセス・タイマー │
            │ ブロッキング用プール: 重い SQL・外部の声の検索・埋め込み・サイドカー │
            └─────────────────────────────────────────────────────────┘
```

- **イベントスレッド**: `asio::io_context` を 1 本のスレッドで回す。共有状態 (レビュー待ちのペーパー、進行中の議論、
  壁打ちのセッション、ペルソナエンジンの状態、設定のライブ値) はこのスレッドだけが触る。mutex は持たない。
- **議論の進行**: 1 議論 = 1 コルーチン。TS の `await` の位置がそのまま `co_await` になる。
- **待ち**: LLM・外部 HTTP・子プロセス・`sleep` は待てる関数 (awaitable) にする。待っている間イベントスレッドは他の仕事をする。
- **ブロッキング用プール**: CPU を使う処理と、長く掛かる同期呼び出しだけを出す。プールの仕事は共有状態を触らず、
  引数を値で受け取り、結果を値で返す。
- **SQLite**: 短い問い合わせはイベントスレッドで同期に呼ぶ (Node 版の better-sqlite3 と同じ)。全件走査や大きな集計は
  プールへ出す。境界は「イベントスレッドの遅延」の計測で決める (§5)。

### コルーチンの型

`boost::asio::awaitable<T>` を使う (Boost.Asio は既存の依存、C++20)。自前のコルーチン型は書かない。
アプリ側のコードは `base/async.hpp` (`di::Task<T>` = `asio::awaitable<T>` の別名と、`di::spawn` / `di::sleep_for` /
`di::on_pool`) だけを見る。今は「Boost を含む翻訳単位は `infra/` だけ」にしてビルド時間を抑えているので、
この別名ヘッダを入れたときのビルド時間を第 0 段で測り、許容できなければ型を消去した薄い自前の待ち型に切り替える。

## 4. 書き方の決まり (コルーチン特有の事故を防ぐ)

1. コルーチンの引数は**値で受ける** (`const std::string&` や `std::string_view` で受けない)。呼び出し元の一時オブジェクトは
   最初の `co_await` で消える。
2. `co_await` をまたいで、参照・ポインタ・イテレータ・`string_view`・範囲 for のループ変数の参照を**持ち越さない**。
   共有状態は `co_await` の後で取り直す (待っている間に他のコルーチンが書き換える)。
3. ラムダをコルーチンにするときは**キャプチャなし**にし、必要な値は引数で渡す。
4. イベントスレッドで**待たない**: LLM・外部 HTTP・子プロセス・重い SQL・ファイルの全読みを同期で呼ばない。
5. プールの仕事からイベントスレッドへは**投函だけ**。投函して結果を待つ形 (同期の往復) は書かない。
6. 中断: 議論ごとに中断の合図を持ち、`co_await` のたびに確かめる。終了時は合図を出し、期限つきで待つ。

1〜3 は ASan で、4 は遅延の計測で、5 は TSan で検査する。CI に ASan/UBSan と TSan を載せることが着手の前提。

## 5. 検査と計測

- **CI**: Release (`-Werror`) の ctest、ASan/UBSan の ctest、TSan の ctest。
- **イベントスレッドの遅延**: 100 ms ごとにタイマーを置き、発火の遅れを測る。250 ms を超えたら warn (何を実行中だったかを添える)、
  2 秒を超えたら error。テストでは閾値超えを失敗にする。
- **並行状況のテスト**: 偽の LLM (応答を遅らせられる) で議論を 3 本同時に進めながら、Discord の返信・承認・HTTP の
  編集を重ねる結合テストを足す。TSan の対象にする。
- **段階ごとの数字**: `std::mutex` の数、スレッド数、`detach()` の数を PR に書く。

## 6. 段階

各段階は単独でマージでき、マージ後も全機能が動く。

| 段階 | 内容 | 終わりの条件 |
|---|---|---|
| 0 | `base/async.hpp`、イベントスレッド、遅延の計測、プール、`sleep_for`。既存のコードは触らない | 部品のテスト、ビルド時間の測定、CI に検査ビルド |
| 1 | Discord Gateway のイベント振り分け、`flow/paper_review_session`、`flow/discord_live` の状態 (`g_mu` と 4 つの表) をイベントスレッドへ | `discord_live` と `paper_review_session` から mutex が無くなる。`run_serial` は不要になる |
| 2 | `Scheduler` / `PeriodicTask` / 進行役・合意スコア・自動 seed・バックアップ・kg-sync・cost-relay のタイマーをイベントスレッドのタイマーへ | 専用のタイマースレッドが無くなる。`PeriodicTask` の待ち合わせが無くなる |
| 3 | `LLMClient::invoke`・`http::fetch`・`proc::run`・サイドカーに待てる版を足し、議論のエンジン (rounds / dialectic / 改善 / 壁打ち / 未来予測) をコルーチンにする | 議論が worker のスレッドを占有しない。並行状況の結合テストが TSan で通る |
| 4 | HTTP ハンドラをイベントスレッドで実行 (長い仕事はコルーチンを起こして即応答)、Slack も同様 | ハンドラ用プールが無くなる |
| 5 | 残った mutex・`detach()`・同期版の入出力を削る。終了処理を「中断の合図 → 期限つきで待つ → 通常の終了」にする | `std::_Exit` と監視タイマーが無くなる。mutex は SQLite のラッパとログの出力先だけ |

第 3 段が最大 (議論まわりで 2 万行超)。第 1・2 段だけでも、イベント駆動の状態からは競合が無くなる。

## 7. リスク

- **書き直しの量**: 議論のエンジンは関数が深く呼び合うので、コルーチンにする範囲が呼び出しの木の全体に及ぶ。
  エンジンごとに分け、期待値 (`native/tests/fixtures/`) が変わらないことで確かめる。
- **`co_await` をまたぐ状態の変化**: 同期のときは起きなかった「待っている間に表が書き換わる」が起きる。Node 版と同じ性質
  だが、移植時に mutex で守って済ませた箇所は読み直しが要る。
- **イベントスレッドの詰まり**: 1 本なので、同期の重い処理が 1 つ混ざると全体が止まる。遅延の計測を先に入れる理由。
- **デバッグ**: コルーチンのスタックは途切れる。ログに議論 ID と段階名を必ず付ける。

## 8. 決めること

1. コルーチンの型は `asio::awaitable` でよいか (第 0 段のビルド時間の結果で確定)。
2. イベントスレッドで SQLite を同期に呼ぶ範囲 (遅延の計測の結果で境界を決める)。
3. 終了時に進行中の議論を待つ上限 (今は 20 秒で打ち切り)。
