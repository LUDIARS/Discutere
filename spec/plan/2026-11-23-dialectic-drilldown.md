# 論拠の形を成していない発言の深掘り

## 0. 依頼と現状

neco (2026-11-23):「論拠の体を成していない場合、深掘りする」。論拠の形は `dialectic.md` §2.5 が定義済み
(演繹 / 帰納 / アブダクションの 3 種類、主張とデータを分ける・論拠が誤れば主張も誤り・限定をはっきりさせる)。
**形を満たさないときにどうするかは未定義**で、今は:

- 反論: データか論拠が無い (`incomplete`)・突く先が無い (`unanchored`)・JSON が崩れた → その場で `question` に格下げ。
  進行役が理由を一言流して次へ進む。聞き返さない。
- 定立: JSON が崩れると主張そのものを根拠に複製して degrade する (論拠の無い根拠が残る)。確かめない。

実測 (直近 3 議論): 形の崩れた反論は 1 議論 0〜7 件。

## 1. 方式

**深掘り = 欠けている要素を名指しして、同じ人に 1 回だけ言い直させる。** 言い直しで形が整えば数え、整わなければ従来どおり。
**深掘りは論拠が不足している場合だけに行う** (neco 2026-11-23): データか論拠が無い・形が崩れて読めない・論拠がデータの言い換え。
突く先が無い (`unanchored`)・種類・範囲・確度・裏付け・例外条件の欠けは論拠の不足ではないので深掘りしない。

### 1.1 反論 (応酬)

1. 応答が `incomplete` (データか論拠が無い) / JSON 崩れ のとき (判定 LLM の `out_of_scope` 等は形ではなく前提ルール違反なので対象外)、
   最初の応答は発話として残す (`question`)。
2. 進行役が定型文で深掘りする:「〇〇さん、その反論には<欠けている要素>がありません。<要素>を添えて言い直してください。」
   欠けている要素は §2.5 の語彙で書く: 反論のデータ (事実・事例・仕様) / 反論の論拠 (そのデータで相手のどこが崩れるか) /
   突く先 (どの根拠のデータ・論拠・限定か)。
3. 同じ人に、元の応答プロンプト + 「# 進行役からの深掘り」節 (欠けている要素と、前の応答の要旨) で 1 回だけ言い直させる。
4. 言い直しを同じゲート (形の検査 → 判定 LLM) に通す。通れば反論として積む。通らなければ `question` + 従来の違反の告知。
5. 深掘りは応答ターンの上限を消費しない (1 ノードにつき 1 回まで)。

### 1.2 定立

定立の JSON が崩れて degrade した (根拠が主張の複製になった) とき、論拠 (warrant) の無い根拠があるとき、
論拠がデータの言い換えのとき、欠けている要素 (データ・論拠) を名指しして 1 回だけ作り直す (向きの作り直しと同じ `feedback` の経路)。

### 1.3 記録と露出

- `ExchangeEnd` に深掘りの件数と、そのうち論拠になった件数を持つ。まとめ文と決着表の「応酬」行に出す。
- 設定 `flow.dialectic.drillDown` (既定 true)。false で従来どおり。

## 1.4 トゥールミンモデルを正しく適用 (neco 2026-11-23、同じ PR)

深掘りが見る「形」をトゥールミンの 6 要素にそろえた (`dialectic.md` §2.5 の表)。v2 までは裏付け (backing) が無く、
限定は範囲だけ、反駁 (rebuttal) は相手の反論の名前に取り違えていた。

- 定立: 裏付け・確度 (`force`)・例外条件 (`exceptions` = 本人が挙げる反駁) を持つ。範囲・確度・論拠が無い、
  論拠がデータの言い換えなら深掘りする。範囲・確度・裏付け・例外条件の欠けは指示文で求めるだけで深掘りしない (論拠の不足ではない)。
- 反論の突く先に裏付け (backing、根拠を指す) と例外条件 (exception、主張全体) を足す。
- 判定・応酬・止揚・決着表は同じ見せ方 (`toulmin.hpp`)。保存は `flow_position.qualifier_force` / `exceptions_json`
  (migration `2026-11-23-position-toulmin`) と `grounds_json` の `backing`。
- 記録の再生 (w4p golden) は深掘りを切って回す (旧記録の定立には確度などが無く、深掘りが走ると応答の順がずれる)。
  深掘りとトゥールミンの効き目は専用テスト (`dialectic_drilldown_tests` / `dialectic_toulmin_tests`) で見る。

**一番効く改善 (別タスク候補)**: 判定系は 1 回あたりプロンプト 1 千字程度なのに、`cache_creation_input_tokens` が約 3.5 万・
`cache_read_input_tokens` が約 2 万ある。費用の大半はこの固定分。推定原因は (a) claude CLI を Discutere のフォルダで起動して
CLAUDE.md・メモリ等を毎回読み込む、(b) 動的な system 節のせいで prefix がキャッシュに乗らない。空の作業フォルダでの起動と
`--exclude-dynamic-system-prompt-sections` で 1 回あたり 1/10 前後になる見込み (未検証、実 LLM で数回測って確かめる)。
`--bare` は ANTHROPIC_API_KEY 必須なので使えない (claude -p は鍵を持たない運用)。

**まとめを参照した発言 (btw 方式)**: 発話者に両陣営の全論拠と応酬の全経路を渡す代わりに、進行役のまとめ (その論点の決着表の行) と
応答対象だけを渡す。発話の呼び出しは今いちばん安い (1 議論 $1.35、全体の 2%) ので費用はほぼ変わらない。効くのは焦点
(話がそれにくい) と速さ。発話プロンプトは平均約 6 千字 → 半分以下の見込み。
