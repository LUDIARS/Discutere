# Discutere 議論エンジン 設計評価レビュー (neon)

## 総合評価: 2 / 5

**一言の理由**: 「発話の列」から「明示的な論証状態機械＋敵対的批准」へ踏み出した再設計の着想と誠実な限界認識は高く評価できる一方、**「ゲーム設計の多軸トレードオフ検討」という本来の目的を「固定賛否の二項ディベート競技」に押し込めた構造的不適合**、**3 世代の仕様積層による設計矛盾（改善フローの空洞化・意見屋の遊休化・収束と結論の不整合）**、および **生成の弱さを後段の検閲 LLM と装飾 LLM で補うコスト過積載** が、設計全体の実用性を大きく損なっている。

## 議論エンジンの目的 (仕様から読み取った定義)

仕様群（`spec/feature/flow/OVERVIEW.md`, `dialectic.md`, `discussion.md`, `improvement.md`, `proxy-debate.md`, `user-voices.md`, `spec/plan/2026-10-13-dialectic-v2-improvement.md`）から読み取れる Discutere 議論エンジンの目的は次の通りである。

> **ゲームの仕様・体験・運営方針に関する問いに対して、プレイヤーの声（外部レビュー・試遊感想）とゲームの資料（メカニクス・ジャンル特性）を根拠に、立場の異なる複数の AI 人物が構造化された検討を行い、作り手が「次に採るべき設計・改善の方向」「条件や見解が割れて保留すべき点」「判断に不足している一次データ」を根拠付きで意思決定できる結論を出すこと。**

本レビューは、現行の設計群（および `e796c5a` 実装での裏取り）がこの目的を果たす設計として妥当か、より良い設計はあるかを評価する。

## 観点 1: 目的との適合

### 1-1. [重大] ゲーム設計の「多軸トレードオフ探索」を、Yes/No 二項対立のディベート競技へ押し込んでいる
- **根拠**: `spec/feature/flow/dialectic.md` §1, §2.5, §2.6, §4.5 / 裏取り: `native/src/flow/dialectic/issues.cpp:12-20`（「賛成側と反対側が本気で対立できる論点」に分解）、`native/src/flow/dialectic/position.cpp:35-38`（`賛成 = 論点に「はい」/ 反対 = 「いいえ」`）。
- **所見**: ゲーム仕様・体験改善の議論は本来、**複数のプレイヤー層（ライト層・コア層・嗜好の異なる遊び手）× 複数の設計軸（手触り・長期継続・収益・開発/運用コスト）** にまたがる設計空間の探索である。これを「賛成 vs 反対の 2 陣営が論拠 1〜3 本をぶつけ合い、論破か止揚かを競う」構造に閉じ込めると、次が起きる。
  1. 「案 A / 案 B / 案 C の比較」や「どの層向けにどこを割り切るか」といった実務的な問いが、論点分解と定立の段階で無理やり Yes/No に潰される。
  2. 価値対立の自然な解（セグメント別の条件分割や段階導入）に辿り着くためだけに、わざわざ極端な賛否の応酬を何十ターンも経由する遠回りになっている。

### 1-2. [重大] 結論の 3 区分（止揚 / 論破 / 結論なし）と出力形式が「作り手の次の手」に接続していない
- **根拠**: `spec/feature/flow/dialectic.md` §4.5, §6 / 裏取り: `native/src/flow/dialectic/outcome.cpp:5-32`, `native/src/flow/dialectic/driver.cpp:594-599`, `native/src/flow/dialectic/conclusion.cpp:79-103`, `native/src/flow/conclusion.cpp:47-108`。
- **所見**:
  - 作り手が結論に求めるのは **「何を採用・変更するか」「成立条件と捨てるトレードオフは何か」「何が未検証で次に何を測るべきか」** である。
  - しかし 3 区分は「弁証法の手続き上の成否」であって意思決定ステータスではない。とくに `facts` 対立が照会で片方を支持（`resolved`）しても区分は「結論なし」（`dialectic.md` §4.5 L167、`driver.cpp:596-599`）、折衷案が両陣営に批准（`compromised`）されても「結論なし」（`outcome.cpp:22-23`）へ落ちる。ゲーム開発実務で最も有用な「条件付き折衷」「事実確認による決着」が「結論なし」に埋没する設計になっている。
  - さらに `dialectic.md` §6 は「現行の直近 20 発話のみを廃止」と謳うが、裏取りでは `conclude_dialectic` が rounds 用の `generate_conclusion` をそのまま呼んでおり（`dialectic/conclusion.cpp:79-103`）、直近 20 発話と投票勝者を入力に使い続けている上、止揚も投票勝者も空なら結論 LLM 自体を呼ばず `(結論なし)` で終わる（`flow/conclusion.cpp:76`）。論証構造と結論生成が設計レベルで断絶している。

### 1-3. [重大] 「改善フロー (`improvement`)」の存在意義が dialectic 既定昇格によって空洞化している
- **根拠**: `spec/feature/flow/OVERVIEW.md` §11-b, §11.5、`spec/feature/flow/improvement.md` 全文、`spec/plan/20260702_respec_from_fable/07-improvement-scoring.md` / 裏取り: `native/src/flow/dispatch.cpp:1557-1563`, `native/src/flow/dialectic/driver.cpp:759-765`, `native/src/flow/dialectic/driver.hpp:43`（`options.evaluateRound は使わない`）。
- **所見**: `improvement.md` は「中立投票をせず、効果予測ベクトルを `design_gap`（目標 `intended_affect` − 現状）へ射影した機械スコアで世論を決める」ことを議論フローとの唯一の差別化としている。ところが `flow.engine = "dialectic"` が既定になった結果、改善フローも `run_dialectic_improvement_flow` へ分岐し、`design_gap` も `effect-predict` も一切使われず、議論フローと同一の中立投票＋弁証法ループが走る設計になっている。2 フローを分ける意味が失われている。

### 1-4. [注意] トゥールミンの `qualifier`（限定）が「反論を弾く盾」として機能しすぎる構造
- **根拠**: `spec/feature/flow/dialectic.md` §2.5 / 裏取り: `native/src/flow/dialectic/rule_check.cpp:49-78`。
- **所見**: 限定の外側からの反論を `out_of_scope` 違反として格下げする規則は、論点ずらしの抑止には効く一方、定立側が狭い限定（例:「コア層に限れば」）を置いたときに「そもそもその限定がゲーム全体の体験対象として狭すぎないか」という実務上の本丸が反論しづらくなる。`attack="qualifier"` は用意されているが、限定そのものを広げる／再定義する手続きが弱く、狭い限定に逃げ込んだ主張が生き残りやすい。

## 観点 2: 役割と進行の構造

### 2-1. [重大] 「意見屋 (`opinion`)」が dialectic エンジンで完全に遊休化し、モデル予算を空費している
- **根拠**: `spec/feature/flow/OVERVIEW.md` §4, §5.2、`spec/feature/flow/model-roster.md` §3, §4 / 裏取り: `native/src/flow/personas.cpp:149-160`, `native/src/flow/dialectic/driver.cpp:176-185, 397`, `native/src/flow/dialectic/exchange_runner.cpp:33-47, 118-120`。
- **所見**:
  - `generate_flow_personas` は残人数の 1/3 を `opinion` に配分し、`model-roster.md` §4 に従い `discussants` の**先頭**（運用設定例では `opus@xhigh`, `opus@medium` という最上位枠）を `opinion` へ割り当てる。
  - しかし dialectic の定立は `pro`/`con` 各 1 名のみ（`driver.cpp:397`）、応酬も `opposing_side(node.side)` の `pro`/`con` しか指名しない（`exchange_runner.cpp:38, 118-120`）。結果、`opinion` は議論中 1 回も発言せず、`persona-setup` の生成対象と表示ログに現れるだけの死んだ枠になっている。
  - かつ `OVERVIEW.md` §5.2 で定義した「意見屋だけにユーザ意見まとめを渡す」分業も、dialectic が全議論者へ論点別の声を直接渡す設計（`driver.cpp:379-380`）に変わった時点で前提が崩れている。

### 2-2. [重大] 賛否のセッション開始時固定が、複数論点にまたがる人格一貫性と衝突する
- **根拠**: `spec/feature/flow/OVERVIEW.md` §1 (L32), §4 (L99-100: 旧記述「ターン時に決定」が残存し自己矛盾), §11.5、`spec/plan/20260702_respec_from_fable/01-persona-state.md`、`spec/feature/flow/proxy-debate.md` §2 / 裏取り: `native/src/flow/persona_setup.cpp:63-72`, `native/src/flow/dialectic/driver.cpp:71-100, 176-180`。
- **所見**:
  - 毎ターン賛否を再抽選する旧仕様の廃止自体は正しいが、その代わりに「セッション全体で全論点を通じて賛成／反対を固定し、その立場に合う価値軸を後から LLM で割り当てる」構造にした結果、**1 つのテーマから分解された 3〜5 個の異なる論点すべてで同じ人物が Yes/No を機械的に演じさせられる**。
  - 現実のプレイヤーや開発者の「人格の一貫性」とは、**価値軸・嗜好の一貫性**であって「すべての論点に常に賛成し続けること」ではない。実際、より新しい `proxy-debate.md` §2 では「立場は論点ごとに本人のデータから決め、対立しなければ反対役を作らない」設計へ到達している。通常議論だけが古い固定賛否を引きずっている。
  - また同陣営に複数 debater がいても、定立は先頭 1 人だけが行い（`driver.cpp:73-79, 397`）、2 人目以降は他人が立てた主張を後付けで防衛するだけの不自然な役割分担になる。

### 2-3. [重大] 論拠の応酬（幅優先 × 上限打ち切り × 三値モデル欠落）が、未決量産と構造バイアスを生む
- **根拠**: `spec/feature/flow/dialectic.md` §2.6 / 裏取り: `native/src/flow/dialectic/exchange.cpp:18-42, 72-118`, `native/src/flow/dialectic/exchange_runner.cpp:109-170`。
- **所見**:
  - **幅優先とターン予算の不適合**: 定立で両陣営が 1〜3 件（計最大 6 件）の論拠を出し幅優先で回すと、深さ 1 で最大 6 ターン、深さ 2 で最大 12 ターンを消費し、既定の `exchangeTurns=16` ではほぼ必然的に深さ 2〜3 の途中で全論拠が中途打ち切りになる。すべての論拠を平等に浅く掘った結果、**1 本も決着しないまま終了する**構造になりやすい。
  - **深さ上限の持ち主有利バイアス**: 既定 `argumentDepth=4`（偶数）では深さ 0(持ち主)→1(相手)→2(持ち主)→3(相手)→4(持ち主・cut) となり、しかも `ground_states()` が `contested` を `defended` に写す（`exchange.cpp:91`）ため、打ち切り＝持ち主防衛成功になる。
  - **障害・違反の誤帰結**: LLM 障害・空応答・ルール違反がすべて `exchange.fail(node.id)` → `status="answered"`（子なし）として閉じられる（`exchange.cpp:28`, `exchange_runner.cpp:106, 161, 168`）。これにより「応答側の API エラー」が「相手の反論の成立（＝自分の親論拠の論破）」に化ける。三値（`standing`/`refuted`/`contested`）に `errored`（未決）を独立状態として持たない設計欠陥である。

### 2-4. [注意] 計測型収束が「論拠の応酬」構造と噛み合っておらず、未討議打ち切りの根拠も薄い
- **根拠**: `spec/feature/flow/dialectic.md` §6、`spec/plan/20260702_respec_from_fable/06-dialectic-core.md` §2 / 裏取り: `native/src/flow/dialectic/driver.cpp:693-713`, `native/src/flow/dialectic/convergence.cpp:7-27`。
- **所見**:
  - 収束条件 3 項目（未応答反論=0 / 投票集中度≥0.6 / 窓内新規 claim=0）は、旧反定立スケジューラ (`scheduler.ts`) の遺物である。論拠の応酬 (§2.6) では応酬中に `claim` が発生しないため、16 ターン応酬すれば窓内新規 `claim=0` が機械的に成立しやすく、意味のある「論点枯渇」を測っていない。
  - そもそも独立した 3〜5 個の論点に分解した以上、論点 1・2 が決着したことを理由に論点 3 を未討議で打ち切る必然性がない（実際、`paper-gate` 由来は打ち切り無効化という例外規定で塞いでいる：`dialectic.md` §6 L244）。収束判定は「論点間の打ち切り」ではなく「1 論点内の応酬の終了条件」として設計し直すべきである。

## 観点 3: 評価・判定の仕組みとトークン・LLM 呼び出しの妥当性

現行設計は **「生成 LLM に構造化出力＋口語雑談を同時にやらせ、その崩れを後段の判定 LLM で何重にも検閲する」** 構造になっており、呼び出し回数と保証内容のバランスが大きく崩れている。

### 3-1. 各仕組みの整理と評価

| 仕組み | 保証しようとしていること | 根拠 | 評価・要否 |
|---|---|---|---|
| **中立レンズ投票** (`run_round_vote`) | 世論（主要意見）の抽出、収束信号 (b) | `discussion.md` §6, `dialectic.md` §6, `driver.cpp:654-688` | **[重大] dialectic では不要かつ有害**。論点の決着（論破/止揚/結論なし）の後に走り決着判定に一切効かないのに `voterCount` 回 LLM を消費し、さらに結論生成へ勝者を流して論証結果を上書きする。 |
| **進行役口語化** (`render_facilitator_line` / `render_nomination`) | 開幕・指名・まとめの自然な口語化 | `dialectic.md` §3, `scheduler.cpp:107-155`, `driver.cpp:370`, `exchange_runner.cpp:125-139, 274-279` | **[重大] 完全に不要**。定型文を言い換えるためだけに最上位モデル `roster.facilitator`（運用例 `opus`、`model-roster.md` §3）を 1 論点 10〜18 回呼ぶ。意味改変リスクしか生まず、失敗時フォールバックの定型文で実務上十分。 |
| **前提ルール判定 LLM** (`judge_rule_violation`) | 範囲外攻撃・藁人形・中身のない却下・論点ずらし・自己矛盾の排除 | `dialectic.md` §2.5, §2.7, `rule_check.cpp:61-136` | **[注意] 目的は妥当だが費用対効果・ペナルティ設計に難**。反論ごとに最大 16 call/論点。障害・ラベル不明時に `ok` へ倒れるため強い保証にならず、違反時にやり直しなく即 `fail()` で相手論拠が成立扱いになる点も過剰。 |
| **「認める」判定 LLM** (`judge_concession`) | 追撃を `concede` に誤分類しない | `dialectic.md` §2.7, `rule_check.cpp:138-165`, `exchange_runner.cpp:174-182` | **[注意] 構造問題の対症療法**。コスト自体は軽いが、1 回の応答に構造化判断（`act`）と雑談口語（`text`）を混在させている根本原因の尻拭い。 |
| **定立の向き判定** (`judge_position_stance`) | 賛否と逆向きの定立を防止 | `dialectic.md` §2.7, `driver.cpp:419-437` | **[注意] 固定賛否の副作用へのパッチ**。コストは 2 call/論点と軽いが、論者が逆向きを言いたくなる原因（その論点が片側に無理筋であること）を検出せず強制再生成してしまう。 |
| **対立型分類** (`classify_tension`) | facts / values / means / tradeoff の分岐 | `dialectic.md` §2, `tension.cpp:38-77` | **[注意] 有用だが入力・語彙が不足**。`claim` と `values` のみで判定し（`tension.cpp:38-44`）、応酬で残った論拠を見ない。また「定義のずれ (`definition`)」型が無く、範囲のすれ違いが `facts` に誤分類される。 |
| **事実照会** (`resolve_fact_tension`) | 事実対立の RAG 検証と未解決の明記 | `dialectic.md` §2, `tension.cpp:79-135` | **[注意] 仕組みが粗く認識論的誤りがある**。キーワード検索上位 10 件（各 200 字）の主観レビューで事実の真偽を `A/B/none` 判定するのは無理があり、かつ `resolved` でも結論なし扱い。 |
| **折衷ゲート** (`elevation_gate`) | 「両方やる」だけの偽止揚の排除 | `dialectic.md` §4, `synthesis.cpp:106-135` | **[注意] 良い着想だが文脈不足**。`elevates` の 1 文だけを見て判定するため（`synthesis.cpp:117`）、論点の問いからのすり替えや崩れた根拠の流用を見抜けない。 |
| **敵対的批准** (`ratify_synthesis`) | 両陣営の根拠の過半保存を機械的に保証 | `dialectic.md` §5, `synthesis.cpp:137-208` | **[重大な穴あり・設計自体は残すべき]** 最良のアイデアだが、①崩れた根拠も分母に含める（`synthesis.cpp:141, 162, 200`）、②`preservedIds` を重複排除せず件数比較するため同一 ID 重複で突破可能（`synthesis.cpp:180-200`）、③論点の問いへの適合（すり替え防止）を見ない、の 3 欠陥で保証が抜け落ちている。 |

### 3-2. [重大] LLM 呼び出し予算の配分が「本質」ではなく「作法と装飾」に偏っている
- **根拠**: `spec/feature/flow/dialectic.md` §9、`spec/feature/flow/model-roster.md` §3, §5。
- **所見**: `dialectic.md` §9 は「3〜4 論点で 30〜50 call」を想定するが、論拠の応酬 (§2.6)＋品質検査 (§2.7)＋進行役口語化＋投票を合算すると、上限 16 ターンに達する論点では **1 論点あたり 55〜65 call（3〜5 論点で 170〜300 call 規模）** に膨張する。さらに最高コストの `facilitator`（Opus 級）を定型文の言い換えに使い、`finalJudgeModel`（Fable 級）を未フィルタ根拠の批准ループ（最大 6 call/論点）に費やしている。**装飾（進行文）と無意味な投票を全廃し、トークン予算は「論拠の生成精度」「決着の構造検証」「実務的な結論整理」に集中させるべき**である。

### 3-3. 足りない仕組み
- **根拠の引用・出所整合のコード検査**: `proxy-debate.md` §3 にある「申告した根拠 ID が束に存在するか・引用が原文に一致するか」の**決定的なコード検査（LLM 不使用）** が通常議論に無い。検閲 LLM を増やすより、まずコードで検証できる事実整合（声 ID・崩れた根拠 ID の除外・重複排除）を徹底すべき。

## 観点 4: 人物像と文脈（Histrio 正本化・アーキタイプ設計案）

### 4-1. [重大] 人物像の仕組みが 4 系統に分裂し、既定の dialectic で遊び手の型が一切効いていない
- **根拠**: `native/src/flow/personas.cpp`（固定 3 風味）、`spec/feature/flow/persona-pool.md` + `native/src/flow/persona_descriptor.cpp`（Voluptas 由来・`preferenceAxes`/`aversions`/`mechanicReactions`）、`spec/feature/flow/proxy-debate.md`（公開発言束）、`E:/Document/Ars/Histrio/spec/feature/virtual-persona-life-script.md`（人生脚本 × OK 牧場） / 裏取り: `native/src/flow/director.cpp:149-158, 274`, `native/src/flow/dialectic/driver.hpp:43`（`possess は使わない`）, `native/src/flow/dialectic/position.cpp:22-48`, `native/src/flow/dialectic/exchange_prompt.cpp:32-102`。
- **所見**: `persona_descriptor.cpp` が丁寧に言語化している `mtg.timmy/johnny/spike` や `style.*`、苦手メカニクス、課金傾向は、rounds エンジンの `opinion` 1 枠にしか憑依されず、既定の dialectic エンジンでは発話プロンプトに一切届いていない。結果、dialectic の論者は実質「名前と 1 文の価値軸だけ違う同一モデル」になっている。

### 4-2. [重大] Histrio の「人生脚本 × OK 牧場」と Discutere の「遊び手の型」は別レイヤーであり、設計方針が正面衝突している
- **根拠**: `E:/Document/Ars/Histrio/spec/feature/virtual-persona-life-script.md` §0〜§5、`E:/Document/Ars/Histrio/spec/feature/persona-chat-engine.md` §0〜§3、`spec/plan/2026-11-23-persona-game-archetype-context.md` §2.1〜§2.3。
- **所見**:
  - **レイヤーの混同**: Histrio の仮想人格仕様は、交流分析（TA）の 6 プロセス脚本（`until`/`after`/`never`/`always`/`almost`/`open_ended`）を反応の主因とし、会話語彙の統計から 5 軸の立場ベクトルと OK 牧場象限を決める **「対人会話・チャット振る舞いエンジン」** である。これは「前提確認を先に求める」「完了直後にリスクを挙げる」といった **議論の進め方の癖（対話行動）** は表せるが、「高難易度アクションのパリィを好む」「ガチャ課金に敏感」といった **ゲームの遊び手としての評価軸（ドメイン選好）** は表現できない。
  - **仕様間の矛盾**: Histrio 仕様 §5 は「論者間の立場ベクトルの差がそのまま討論の対立軸になる」と設計しているのに対し、アーキタイプ設計案 §2.1〜§2.2 は「立場 (pro/con) は固定し、人生脚本は会話反応 1 行の添え物に留める」としている。これでは Histrio の反応表・OK 牧場・判断ログの大半を使わず、未実装サービスへの外部 HTTP 依存だけを抱え込むことになる。
  - **正本の正しい分け方**: Histrio を「人物像の正本」に置く方針自体は、公開発言からの人物像形成（`proxy-debate.md` §6）や複数サービス横断の対話スタイル統一としては理にかなう。ただし **① 対話行動層（Histrio: 人生脚本・口調・会話操作）** と **② ゲーム選好層（Voluptas / Di: 遊び手の型・嫌悪メカニクス・経験ジャンル）** を明確に分離し、Discutere の議論の主軸には ② を据え、① は補助（議論の癖・多様性）に限定する契約にすべきである。

### 4-3. [注意] アーキタイプ設計案の「全キャスト憑依 (D3)」は固定賛否と衝突する
- **根拠**: `spec/plan/2026-11-23-persona-game-archetype-context.md` §2.2, §4 (D3)。
- **所見**: 賛成・反対の両陣営に遊び手の型を持たせる方向（D3）自体は不可欠だが、「立場はセッション開始時に機械固定し、型は立場を変えない」（§2.2）とすると、「課金慎重な探索型」に「青天井ガチャ賛成」を演じさせるような内的矛盾が発生し、詭弁や `self_contradiction` を増やす。型を本当に効かせるなら、**① 論点ごとに型から自然な立場を導く（`proxy-debate.md` §2 と同型）** か、**② 少なくとも賛成／反対に整合する型をプールから選定する** 仕組みとセットにする必要がある。

### 4-4. [注意] ゲームの型（Ludus `game-template` 利用・D1/A2）は有望だが、ジャンル網羅性と抽出対象の選定に注意が要る
- **根拠**: `spec/plan/2026-11-23-persona-game-archetype-context.md` §2.1, §2.3, §4 (D1)、`E:/Document/Ars/Ludus/spec/data/game-template/README.md`, `action/INDEX.md`, `action/ux/player_experience.md`, `vampire_survivors_like/INDEX.md`。
- **所見**:

  - とくに `action/ux/player_experience.md` のような **「体験フロー」「上達感の仕掛け」「NG パターン（理不尽・飽きる・テンポが悪い等）」** は、議論の共通前提として非常に質が高い。

    1. **17 ジャンルの網羅性不足**: Ludus の 17 ジャンルは PC/CS のゲームプレイ型が中心で、モバイル運営型ゲーム（例: モンストのようなひっぱりアクション＋マルチ協力＋ガチャ運営）が綺麗に当てはまらない。無理に `action`（SEKIRO/DMC 前提）等を当てると、的外れなコアループが議論を歪める。**「当たらないときは載せない」原則の徹底**に加え、プレイジャンル軸とは別に **事業・運用モデル軸（買い切り / ライブサービス運営型 / 競技 PvP 等）** を分けて持てる設計が望ましい。
    2. **抽出元の偏りリスク**: 各ジャンルの `INDEX.md` は 60fps・SoA・アクター設計など実装仕様の比率が高い。議論に渡すべきは `ux/` 配下のプレイヤー体験と NG パターン、コアループであり、抽出スクリプトの入力仕様を明示する必要がある（なお全 17 ジャンルに `ux/` が揃っているかは未確認であり、実装前に要確認）。

## 観点 5: 根拠の扱い

### 5-1. [重大] 「事実」「プレイヤーの声（主観サンプル）」「ゲーム仕様」「LLM 推測」の区別が通常議論で破綻している
- **根拠**: `spec/feature/flow/dialectic.md` §2, §2.5、`spec/plan/20260702_respec_from_fable/08-paper-provenance.md`、`spec/feature/flow/proxy-debate.md` §3 / 裏取り: `native/src/flow/dialectic/tension.cpp:79-135`, `native/src/flow/dialectic/driver.cpp:379-380`。
- **所見**:
  - `08-paper-provenance.md` の「curated と LLM 仮説メカニクスの節分離」や `proxy-debate.md` §3 の「引用・言い換え・推測のコード検証」は極めて良い設計である。
  - しかし通常議論の定立・反論では `data` が自由テキストのままで、**確定仕様・プレイヤーの声・LLM の一般知識/推測が機械的に区別されない**。

  - さらに `resolve_fact_tension`（`tension.cpp:104-135`）は、客観的事実（売上・継続率・離脱理由など）の対立を「外部の声（主観レビュー 10 件）」で `A/B` 判定しようとしている。公開レビューは「継続中の熱心な層」や「極端な不満層」に偏るサンプルであり、事実の真偽証明の証拠にはならない。

### 5-2. [重大] 崩れた論拠・撤回された論拠・未決の論点が、止揚・批准・結論へ素通しで混入する
- **根拠**: `spec/feature/flow/dialectic.md` §4, §5, §6、`spec/plan/2026-10-13-dialectic-v2-improvement.md` §2 (P3) / 裏取り: `native/src/flow/dialectic/synthesis.cpp:28-33, 81-84, 137-208`, `native/src/flow/dialectic/conclusion.cpp:34-103`, `native/src/flow/conclusion.cpp:58-80`。

  - **結論の汚染**: 結論生成が構造化決着表を本文に直書きせず、自由文 LLM に「直近 20 発話＋投票勝者＋要約」から作文させるため、撤回された魅力的な推論や未決論点の主張が結論の前提として容易に復活する。

### 5-3. [注意] 証拠の偏り（生存者バイアス）の制御が開始ゲートから外れ、結論への反映も弱い
- **根拠**: `spec/plan/20260702_respec_from_fable/09-paper-gate-debatability.md` / 裏取り: `native/src/flow/debatability.cpp:190-222`（L213-214 で `r.debatable = !issues.empty()` へ緩和され、`minArmableIssues` による再提案が無効化されている）。

## 観点 6: 測り方

### 6-1. [重大] 「コストの測り方」はあるが、「議論の質の測り方」が通常議論に欠落している
- **根拠**: `spec/feature/flow/OVERVIEW.md` §8、`spec/feature/flow/proxy-debate.md` §5、`spec/plan/2026-10-13-dialectic-v2-improvement.md` §1, §5, §6。
- **所見**:
  - `OVERVIEW.md` §8 の全呼び出しコストログは優秀だが、アウトプット品質の定量指標が無い（`proxy-debate.md` §5 だけが判別精度・根拠付き率・誤帰属率というまともな評価設計を持つ）。
  - `v2-improvement.md` §5 の受入基準は「モンストの 1 議題・ペーパー #143 を使い回して Fable / Astra に 4/5 以上を貰う」となっている。これには 2 つの重大な罠がある：
    1. **単一題材への過適合**: 1 本の運営型ゲームの事例に最適化すると、買い切りゲームや企画段階（機密）案件での劣化に気づけない。
    2. **LLM 審査官の作法バイアスへの過適合**: AI レビューは「論理の整合性・手続きの綺麗さ」を高く評価しやすいが、「作り手にとって本当に新しい気づき・次の一手になるか」とは必ずしも相関しない。

### 6-2. [注意] 測れる部分と測れない部分を分けた 3 層評価設計が必要
- **自動計算で測れる部分（設計に追加すべき）**:
  - **構造健全性メトリクス**（DB から LLM なしで算出・版比較可能）: 論拠の決着率（自然終了率 vs 打ち切り率）、`errored` 率、ルール違反率、批准 1 回目通過率、崩れた根拠の止揚/結論への混入件数（0 件必須）、有効な声 ID 参照率、1 論点あたりコスト・レイテンシ。
- **固定ベンチマークで測れる部分**:
  - 性質の異なる **5〜8 件のゴールデン議題セット**（例: ライブサービス運営 / 買い切りアクション / 機密の新作企画 / 事実材料が乏しい議題 / 定義ずれを含む議題）を用意し、版を上げるときに構造指標＋人間/AI の差分比較を行う。
- **設計上、自動では測れない部分（人間の実務指標が必須）**:
  - **意思決定への実効性（Actionability）**: 「作り手が結論を読んで実際に仕様変更・検証タスク作成・見落とし発見につながったか」。これは AI 審査では永遠に測れない。結論画面や Discord まとめに作り手用の軽量評価（例:「次の手に使えた / 気づきあり / 使いにくい」＋ 1 行理由）を付け、版 (`engine_version`) ごとに集計する仕組みが必要である。

## 観点 7: v2 改善設計とアーキタイプ設計案の評価

### 7-1. v2 改善設計 (`spec/plan/2026-10-13-dialectic-v2-improvement.md`)
- **方向の妥当性**: **「記録と結論の誠実性を回復する止血策」として方向は正しい**。とくに P1（打ち切り告知と内訳）、P2（`unsettled` 導入）、P3（崩れた根拠の遮断＋決着表のコード直書き）、P4（声の固定番号と一覧）は、現状の最も恥ずかしい破損（撤回済み論拠の復活・打ち切りの隠蔽・検証不能な引用）を直接直す。
- **設計の穴**:
  1. **[重大] 打ち切り量産の根本原因を直していない**: 幅優先 × 最大 6 論拠 × 上限 16 ターンのまま `argumentDepth` を 4→5 に伸ばすと、むしろターン消費が増えて打ち切り・`unsettled` が増える。P1/P2 だけでは「正直に全滅・未決と報告するだけの議論」になる恐れが高い。
  2. **[重大] 障害応答 (`fail()` / `errored`) の分離が抜けている**: 応答 LLM の障害・空応答で相手の反論が成立してしまう穴が P1〜P11 に記載されていない。
  3. **[重大] 不要 LLM の削減がなく、検閲 LLM をさらに増やしている**: dialectic 投票と進行役口語化 LLM を放置したまま、P3 結論文検査 LLM・P8 メカニクス矛盾検査 LLM を足そうとしている。まず不要な呼び出しを削り、コードで保証できる範囲（決着表直書き・入力からの崩れた根拠除去・重複排除）を徹底するのが先である。
  4. **[注意] P8・P9 の具体性不足**: P8（`mechanic_mismatch`）はペーパーの簡略なメカニクス記述と照合するため誤検知（正当な体験議論の格下げ）リスクが高い。P9（声の偏り内訳）は「続けている人 / 離脱・不満 / 不明」をどう分類するか（LLM か既存感情極性か）の設計が未定義。
  5. **[注意] `opinion` 遊休枠と `improvement` フロー空洞化がスコープ外のまま放置されている**。

### 7-2. アーキタイプ設計案 (`spec/plan/2026-11-23-persona-game-archetype-context.md`)
- **方向の妥当性**: **「遊び手の型 × ゲームの型」を議論の前提に据える着想は極めて妥当**で、D2（A1・A2 を Di 側で先に進め、Histrio 接続 A3 は別タスク）の段階分割も現実的である。
- **設計の穴**:
  1. **[重大] 固定賛否のまま全キャストに型を付ける矛盾（D3）**: 観点 4-3 の通り、型と固定スタンスの衝突を解く配席／論点別立場決定の設計が抜けている。
  2. **[重大] A3（Histrio 人生脚本）の責務境界が未整理**: 観点 4-2 の通り、ゲーム議論の選好軸と TA の人生脚本の役割分担を再定義しないまま接続すると、薄い 1 行プロンプトのために外部サービス依存とレイテンシ（1.5 秒）を増やす結果になる。
  3. **[注意] A2（Ludus 17 ジャンル）の非対応ジャンルと抽出粒度の未定義**: 運営型モバイルゲーム等の受け皿と、`ux/` 優先抽出の仕様が要る。

### 7-3. 優先順位の提案
1. **最優先（止血と純化）**: 不要 LLM の撤去（進行役口語化・dialectic 投票）＋ 状態機械の整合修復（`unsettled` / `errored` 分離、批准の生存根拠分母化と重複排除、決着表のコード直書き、声 ID 固定・一覧出力 [P1, P2, P3 前半, P4]）。
2. **第 2 優先（価値の核）**: 結論出力を「作り手の意思決定シート」へ再設計 ＋ 応酬の打ち切り対策（論拠数の絞り込みまたは深さ優先化）＋ `opinion` 遊休枠の解消とアーキタイプ A1（`persona_descriptor` 配線＋型と立場の整合）。
3. **第 3 優先（文脈と統合）**: `definition` 型 (P5)、アーキタイプ A2（Ludus `ux/` 中心＋事業モデル軸）、改善フロー (`design_gap` 効果予測) の dialectic 統合、ベンチマーク評価セット構築。
4. **見送り・再検討**: P3 後半の結論文検閲 LLM、P8（`mechanic_mismatch` 検閲 LLM）、A3（Histrio 人生脚本接続は責務境界の再設計後）。

## 観点 8: 代わりの設計

ゲームの仕様・改善を考えるという本来の目的に対し、現行の「固定賛否の 1 対 1 論拠 BFS 応酬＋止揚批准」と対比して、より適合度の高い代替設計を 2 案示す。

### 代替案 A（本命推奨）: 「設計レビュー（RFC Critique）× 多視点アーキタイプ探索」モデル

二項ディベート（賛成 vs 反対の勝敗）をやめ、**優れたゲーム開発チームの設計レビュー会議** を状態機械化する組み方。

```
[0] 人間ゲート（現行 08/09 を継承・拡張）
    - 薄い共通地盤（確定仕様 + ゲームの型 UX/NG パターン + 固定番号付きの声一覧 + 偏りサマリ）
    - 人間が「論点」と「比較したい設計案 (Option A / B / 現状維持)」を承認・編集

[1] 独立クリティーク（並列・同調バイアス遮断、3〜4 アーキタイプ × 各 1 call）
    - 賛否は固定しない。異なる遊び手の型（例: コア上達型 / ライト探索型 / 課金慎重型 / 運用収益視点）が、
      他者の発言を見ずに構造化評価を出す:
      { 評価 (支持/条件付き支持/懸念), 根拠 ([V#]/確定仕様/推測を明示), 条件・代替案, 不足データ }

[2] 焦点化クロスレビュー（コードが実際の対立点だけ抽出・深さ優先・最大 2 往復）
    - 全員一致した論点は無理に反対役を作らず「合意」として即確定
    - 意見が割れた核心 1〜2 点だけ、対立する 2 者の間で深さ優先 1〜2 往復の集中応酬
    - 根拠の引用整合はコード検査（LLM 不使用）。反論検閲 LLM は置かず、構造欠損のみコードで弾く

[3] 設計案の統合 ＋ 敵対的リスクチェック（現行の敵対的批准を発展継承）
    - 進行役が「推奨案（条件分割・段階案）＋捨てるトレードオフ＋検証すべき仮説」を生成
    - 各アーキタイプが「自分の懸念が解消されたか / 残るリスクは何か」をチェックリストで敵対確認
    - ※ 改善フロー (improvement) では、ここで出た複数候補案に対して design_gap 効果予測スコアを算出し、
      案の優先順位付けに使う（議論と改善が 1 骨格で統合される）

[4] 決定的な意思決定シート出力（コード生成が本体＋LLM は冒頭 3 行要約のみ）
    - ① 合意事項  ② 条件付き推奨案とトレードオフ  ③ 未解消の対立・リスク
    - ④ 次に取るべき検証（不足している一次データ・見るべき KPI/試遊項目）  ⑤ 参照した声一覧
```

### 代替案 B（低コスト進化版）: 「現行 dialectic の最小純化（深さ優先 1 本勝負＋決定論的集計）」モデル

現行の「論拠の応酬＋止揚批准」のコード資産を最大限生かす場合の組み替え。

- **変える点**:
  1. 定立の論拠を各陣営 **最強 1〜2 本に絞り、幅優先ではなく 1 本ずつ深さ優先で決着** させる（途中でターン上限に達しても、1 本目は決着済みになる）。
  2. 進行役口語化 LLM・dialectic 投票・過剰な後付け検閲 LLM を全廃する。
  3. 事実対立は「外部の声での真偽判定」をやめ、コードで関連声を束ねた上で「要一次データ確認リスト」へ直接出力する。
  4. 結論はコード生成の決着表＋「作り手の次の手・不足データ」節を本体にし、`generate_conclusion` 共用を断つ。

### 現行設計 vs 代替案の比較

| 比較軸 | 現行設計 (`dialectic` e796c5a) | 代替案 B（最小純化） | 代替案 A（設計レビュー型・推奨） |
|---|---|---|---|
| **ゲーム改善目的との適合** | 低（Yes/No 競技・3 区分が意思決定に直結しない） | 中（誠実で整理された論点表は出るが二項対立の制約は残る） | **高**（多層プレイヤー評価・案の比較・次の一手と検証項目が直接出る） |
| **人物像（遊び手の型）の効き** | 低（未配線＋固定賛否と衝突） | 中（配線できるが固定賛否との矛盾は残る） | **高**（型から自然な評価と対立軸が導かれる） |
| **LLM 呼び出し数（3 論点目安）** | 過大（~150〜200 call） | 低〜中（~45〜70 call） | **低（~25〜45 call・Phase 1 並列可）** |
| **打ち切り・未決の起きにくさ** | 低（幅優先 6 論拠でほぼ全滅） | 高（1 本ずつ深さ優先で決着） | **高**（核心 1〜2 点に集中・2 往復完結） |
| **改善フロー (`design_gap`) との整合** | 破綻（dialectic 既定で死文化） | 未解決（別途配線が要る） | **統合**（候補案の優先順位付けに自然に組み込める） |
| **変更規模** | — | 小〜中（既存 dialectic の改修） | 中〜大（ドライバと出力形式の再設計） |

**推奨**: 短期では **代替案 B（v2 の止血＋不要 LLM 撤去＋深さ優先/論拠絞り込み）** で現行エンジンの信頼性を直ちに回復しつつ、中期の本命設計としては **代替案 A（設計レビュー型）** へ移行する二段構えが最も合理的である。

## 設計として直すべきこと (上位 5 件)

1. **[重大] 出力とゴールを「弁証法の手続き結果」から「作り手の意思決定シート」へ転換する**
   - `dialectic/conclusion` の `generate_conclusion` 共用を断ち、決着表（全予定論点・生存/崩壊/未決根拠・批准結果・未討議）をコードで直書きする。さらに「条件付き採用案」「捨てたトレードオフ」「判断に不足している一次データ・次の検証手」を明示し、批准済み折衷や事実照会結果を「結論なし」へ埋没させない。
2. **[重大] 論拠の応酬の状態機械（`unsettled` / `errored`・批准分母・打ち切り構造）を根本修正する**
   - 打ち切りを `unsettled`、障害/空応答を `errored` として `defended` / `answered` から分離し、崩れた根拠を止揚入力と批准分母から除外・重複排除する。あわせて「幅優先 × 6 論拠 × 上限 16 ターン」の未決量産構造を見直す（論拠数絞り込みまたは深さ優先化）。
3. **[重大] 不要・有害な LLM 呼び出し（dialectic 投票・進行役口語化）を撤去し、検閲 LLM の積層を止める**
   - 決着後に走って結論を汚染する dialectic 投票と、最上位モデルで定型文を言い換える進行役レンダリングを廃止する。根拠の整合検査は `proxy-debate` のように決定的コード（固定声 ID・出所ラベル）で保証し、LLM 予算を本質的な推論に集中させる。
4. **[重大] 人物像の配席・責務境界を再設計する（`opinion` 遊休解消・型と賛否の整合・Histrio 境界）**
   - dialectic で発言しない `opinion` 枠を解消し、`persona_descriptor`（遊び手の型）を議論者プロンプトへ配線する。型を効かせるなら固定賛否をやめ論点ごとに立場を導く（または型に整合する配席にする）。Histrio は「対話行動層（人生脚本・口調）」、Di/Voluptas は「遊び手選好層」と責務を分離する。
5. **[重大] 改善フロー (`design_gap` 効果予測) の空洞化を解消し、議論品質の継続的な評価基盤を設計する**
   - `dialectic` 既定化で死んでいる改善フローの `design_gap` 評価を統合設計する（例: 候補案・止揚案のスコアリング）。同時に、単一議題＋AI レビュー依存から脱却し、複数ジャンルのベンチマーク議題セット・DB 算出の構造健全性メトリクス・作り手からの実務有用性フィードバックの 3 層評価を設計に組み込む。

## 残すべき良い判断

1. **「テキスト→テキストの雰囲気判定」を排し、明示的な論証状態機械＋決定的なコード制御を中核に置いたこと** (`dialectic.md` §0, §3) — LLM に状態遷移や収束判断を委ねない原則は今後も崩すべきでない。
2. **「折衷」と「止揚」の区別（折衷ゲート）と「敵対的批准（reject デフォルト＋根拠 ID チェックリスト）」の着想** (`dialectic.md` §4, §5) — 同調バイアスを抑え「都合のよいまとめ」を防ぐ仕組みとして極めて優れており、代替案 A でも「敵対的リスクチェック」として継承すべき核である。
3. **「事実対立」を弁証法の対象から外し、未解決を隠さず結論に明記する誠実性の原則** (`dialectic.md` §2, §8) — 「分からないことを分からないと言う」規律は、作り手の意思決定ツールとして最も重要な美点である。
4. **ペーパーを「出所明示 (`curated` / `llm` / `crawl`) の薄い共通地盤」とし、論点分解を人間レビューゲートへ前倒ししたこと** (`08-paper-provenance.md`, `09-paper-gate-debatability.md`) — 議論の質の上限を決める論点設計に人間が介入できる配置は非常に的確である。
5. **代理議論 (`proxy-debate.md`) における設計規律** — 論点ごとのデータ起点の立場決定（無理に対立を作らない）、帰属区分のコード検査（原文照合＋推測降格）、定量的評価 (`eval:proxy`) と実測に基づく基準見直し（推薦予測を必須から外した判断）は、通常議論側へ逆輸入すべき模範設計である。
6. **機密／内部タグでの外部の声の完全遮断 (`gateExternalVoices`) と想定意見の明示タグ付け** (`OVERVIEW.md` §3, §5.4) — 未発表企画を扱う実務要件と由来透明性を両立できている。
7. **全 LLM 呼び出しのコストログ計測 (`withCostLog`) とペーパー system 固定によるキャッシュ戦略** (`OVERVIEW.md` §8, `dialectic.md` §5-3) — 設計改善の費用対効果を定量検証できる土台として必須である。
