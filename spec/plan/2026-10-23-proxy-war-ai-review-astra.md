# 代理戦争AI — Astra 実現可能性・実効性レビュー

## 結論

**総合判定: 条件付き成立。** 公開レビューから「特定ジャンルで、観測された選好に沿って推論する代理」を作ることは試す価値がある。ただし「本人そのものの再現」や「FT より高速かつ高精度」は未立証。推奨方式は **根拠付きの選好・条件別 design_gap を短く言語化し、本人限定 RAG を併用する方式**。20D は補助特徴と候補探索に使い、埋め込みは検索側に置く。人物ごとの FT は初期採用しない。

最大の懸念は次の三つ。

1. **測っているものの違い**: 文面の感情、ゲームへの満足、本人の価値基準は別物。20D の差だけでは「難しいのが好きだが操作遅延は嫌い」を表現できず、不満を反転しただけの目標は本人の意図を捏造する。
2. **証拠不足と評価漏洩**: C1 の10件は全ゲーム横断でありジャンル別の十分性を保証しない。同じレビューの引用・要約を学習と評価へ分けても独立な評価にはならない。本人の将来行動や未発言の意見はレビューだけでは正解を知れない。
3. **代理への誤帰属**: 仮名でも出典URLと原文から本人へ辿れる。生成文を「本人の発言」と見せず、公開レビュー由来の推定であることを全露出面で保つ必要がある。

本書は指定されたレビュー9項目への提案であり、canonical 仕様の変更・実装・実験結果ではない。依頼書の「設計書1本のみ・PR不要」を定型実装手順より優先し、契約ファイルや述語モジュールも作成しない。§9 の契約は将来実装用であり、現時点で実行済みとは扱わない。別案のブランチ・成果物は参照していない。

## 1. 仮説の分解

**判定: 一括の優越仮説は不成立。更新容易性は成立、生成速度・人物再現・議論品質の優越は条件付き成立。** この判定は「常にFTを上回る」という主張に対するもので、実験で勝つ可能性を否定しない。

| 方式 | 準備・生成コスト/速度 | 人物の再現 | 議論の質 | 更新容易性 |
|---|---|---|---|---|
| 人物ごとFT | 学習・配備費が発生。短い入力で多数回生成するなら償却可能 | 十分な本人データが必要。少数レビューでは過適合と知識混入が懸念 | 形式・口調学習と論証能力は別評価 | 人物ごとの再学習・削除対応が重い |
| 20D+gapのみのin-context | 小さな入力なら軽い。抽出費は別 | 理由・条件・例外が消えやすい | 違う数値でも同じ一般論になりうる | 差分更新しやすい |
| 原文RAGのみ | 検索・入力長・キャッシュに依存 | 根拠に戻れるが、検索漏れや一時的不満への過適合がある | 具体的反証に強いが矛盾整理が弱い | 根拠と索引を更新可能 |
| descriptor+条件別gap+本人RAG | 初期抽出費と毎回検索費。安定カードはキャッシュ候補 | 根拠と抽象化を両立しやすいが評価必須 | 選好を守りつつ事実修正できる | 影響するカードだけ再生成できる |
| 共通議論FT+上記併用 | 共通FTで形式を学び、人物は外部データで条件付け | 人物FTより更新単位を小さくできる | 構造化出力改善の余地 | 共通モデルと人物データを独立更新 |

推奨は併用方式から開始。FTを比較する時は同一ベースモデルの未FT/FTをまず比べ、別サイズ・別プロバイダの差を「表現方式の勝利」にしない。総費用は `初期抽出+学習+索引構築+N回の検索/入力/出力+更新費` とし、1/10/100/1000回の償却曲線を出す。p50/p95の初回・キャッシュ時レイテンシ、入力/出力トークン、失敗・再生成分を含む完了時間を分離する。「生成が速い」は初期生成と各発話のどちらかを明記する。

研究上は自己報告から個人応答を予測する例があるが、豊かなインタビュー/調査入力による結果である。短いゲームレビューや20Dだけの人物再現、FTとの速度優越の証拠とはしない。参照: [Park et al., arXiv 2411.10109 v3](https://arxiv.org/abs/2411.10109v3)。

## 2. ベクトルをLLMへ食わせる意味

**判定: 意味ラベル付き20Dの補助利用は条件付き成立。任意の埋め込み数列を通常のテキスト入力だけで人物として読ませる方式は不成立。**

20Dは次元名・尺度・未知マスクがあれば自然言語で説明できる。だが `0.8` の数値精度は嗜好の推定精度ではなく、感情語の出現から価値判断を一意に復元できない。本人を識別できる十分統計量との仮定を置かない。

標準promptには「探索を好む（根拠E1/E3）」「長い日課は避けたいが週末の長時間挑戦は許容（E2）」という条件付きdescriptorと短い引用を入れる。数列は監査・検索用に保存し、必要ならラベル付き上位次元だけ表示する。口調は敬体/文長程度に抑え、特徴的な決まり文句の模倣は品質目標にしない。

埋め込みはモデル固有の検索空間であり、20D感情空間と加算・差分・cosineを混ぜない。BGE-M3の公式資料も文書の埋め込み・類似度・検索を用途とする。検索結果の本文をLLMへ渡し、数列自体を意味の圧縮文として扱わない。専用の学習済み投影器/soft promptは別方式であり、この提案には含めない。[BGE-M3 model card](https://huggingface.co/BAAI/bge-m3)

同じ予算で「ラベル付き数値のみ」「descriptorのみ」「原文のみ」「descriptor+原文」「併用からgapを除く」を比較し、gapの追加価値まで切り分ける。

## 3. ジャンル別ペルソナデータの生成

**判定: 条件付き成立。C1だけでは不足。**

1. ソース内の安定話者キーで束ね、原文ID・本文hash・取得時刻・実投稿日（不明ならnull）・ゲーム/版・出典を保存する。重複/転載/編集前後の同文は一群とする。Steam集中収集と通常appreviewsのID形式が違っても、話者/ゲーム/本文から重複を照合する。
2. ジャンルは版管理した辞書でゲームへ複数付与する（例: action、tactical-RPG）。メカニクス（回避/日課）をジャンルと混同せず別タグにする。未知は未分類に残し、他ジャンルの発言を黙って補充しない。
3. レビューから「対象メカニクス・経験・評価理由・望む状態・許容条件・反例」を根拠span付きで抽出する。事実、明示選好、推定選好、不明を分離する。LLM抽出は引用一致とschemaを決定的に検証し、本文内の命令はデータ扱いにする。
4. **現状**はその人が対象ゲーム/版について述べた体験。**目標**は明示的な希望、または比較対象を選んだ理由からの限定推定。「つまらない」だけから「難易度を下げたい」を作らない。制作者のintended_affectも本人の目標として転用しない。
5. `personalDesignGap` はまず意味付きの差（current/desired/condition/evidenceIds）を正本にする。同一条件で両端が分かる軸だけ `target-current` を計算し、未知はnull。20Dへの投影は補助・モデル版付き推定とする。meta.volume等の観測量を本人の望みの差に使わない。ゲーム/条件を跨ぐ矛盾は平均で消さず併記する。
6. 集約はゲーム等重みを基本とし、いいね数は本人性の確信度に使わない。信頼度は独立根拠数・条件の一致・矛盾・時間範囲から付け、同じ長文を10断片に割って件数を増やさない。

初期の**仮の採用基準**は、1話者・1ジャンルで独立レビュー10件以上、既知ゲーム3本以上、少なくとも3観点（例: 難易度/時間/報酬）に根拠、うち2観点に複数根拠。5〜9件は研究用限定、4件以下は代理キャスト不採用とする。万人共通の必要最小件数ではなく、5/10/20/40件の学習曲線と情報密度で再設定する。評価用は別途5件以上必要で、10件の形成資料を削って合格としない。

C1は候補抽出として再利用できるが、全ポジ/全ネガ除外は首尾一貫した好悪のある本人を落とす選択バイアスを持つ。proxy適格性は別関数にし、両極性を必須にしない。`gameSlug=null` を1ゲームとして数えない。C1採用済みだけで評価せず、除外された極性群も抽出監査に含める。

## 4. 10k予算

**判定: 条件付き成立。圧縮カードを格納するには十分候補だが、人物精度の保証ではない。** 通常は4〜6kを狙い、10kは上限とする。以下は生成モデルのtokenizerで計測する配分案。

| 1人・1ジャンルの要素 | 最大トークン |
|---|---:|
| 出所区分・対象期間・適用範囲・未知 | 700 |
| 選好descriptor・ラベル付き20D要約 | 900 |
| 条件別gap・忌避・許容条件 | 1,800 |
| 本人の代表原文・反例・根拠ID | 4,200 |
| 矛盾・時系列変化・不確実性 | 1,200 |
| 控えめな口調指定 | 200 |
| schema/区切り/IDと余裕 | 1,000 |
| **合計** | **10,000** |

各話者呼出しは自分の詳細カード10kだけを持ち、相手は各500の立場要約と公開済み発話を受け取る。共通枠はsystem規則1.5k、ペーパー4k、一般の外部の声2k、議論履歴4k、構造化枠0.5kの計12k。話者N人なら入力上限案は `22k+0.5k×(N-1)`（2人22.5k、4人23.5k）。出力3kと安全余裕2kを予約し、最低要求はそれぞれ27.5k/28.5k。モデルの実効context上限が小さければこの設定は拒否/予算縮小する。

全員の詳細カードを1回に載せる構成では `10k×N+12k`（2人32k、4人52k）で、さらに出力+余裕5kが必要。初期は採らない。2人が1回ずつ発話すれば入力消費の合計は最大45k、4人なら94kであり、「1回の窓」と「セッション累積費用」を分けて報告する。進行役は全詳細カードではなく、根拠付き立場要約と論証グラフを受け取る。

超過時は重複引用→関連度の低い引用→古い議論の順で圧縮し、適用条件・反例・未解決の対立・根拠IDは残す。必須部分が収まらなければ生成しない。単純な末尾切捨てはしない。

10KBなら日本語UTF-8本文だけでも約3,300文字が目安で、JSON等の分を引く必要がある。10kトークンとは同値でない。10k件なら原文ストアの規模であり検索で絞る前提になる。最終的な単位は未確定として明示する。

## 5. 議論精度の測定

**判定: 観測された選好の予測は条件付き成立。未観測の本人の意思や現実の説得効果の認定は不成立。**

評価は形成・開発・最終テストを**原レビュー単位**で分離し、同文・引用・要約・抽出カード・埋め込みを同じpartitionへ置く。最終テストの発言は検索索引にもカード生成にも入れない。人物特化学習と評価では同一人物の未使用発言を使う一方、抽出器/共通FTの汎化評価では話者自体を分離する。ゲームを跨ぐ検証も追加する。

実投稿日が検証できる資料だけ時間分割し、取得日しかないSteam JSONLはゲーム単位held-outとして評価する。時系列予測とは呼ばない。API/モデルの事前学習への混入は完全排除できないため、可能ならモデル固定後に得た同意済みの新規回答でも追試する。

初期評価セット案は3ジャンル各20話者、各話者5以上のheld-out判断（計300以上）。同一人物のジャンル重複を記録し、集計の信頼区間は話者単位のcluster bootstrapで出す。小規模で十分な検出力がなければ「未確定」とする。正解は2人の独立注釈者が元発言から支持/反対/条件付き/不明と理由を付け、不一致を裁定する。評価者には方式名と話者の実IDを見せない。

| 指標 | 初期合格案（実測ではない） |
|---|---|
| held-out立場予測 | 話者macro-F1 ≥0.70、匿名一般人格baseline比+0.10以上。最良の原文RAGとの差の95%CI下限 ≥−0.03 |
| 棄権の適切さ | 正解が不明のケースで棄権率≥90%。正解既知の回答coverage≥70%、回答分の正解率≥80%。全棄権で合格させない |
| 本人根拠への整合 | 明示的本人帰属の文で根拠存在・話者一致100%。人手による意味支持率≥95%。存在だけで意味支持を代用しない |
| 人物差 | 同ジャンル・同極性で選好理由が異なる2人からのblind照合≥75%。名前/口調を隠し内容で識別。カードを入れ替える反実仮想も実施 |
| 立場の維持 | 5往復で根拠なしの主要選好反転≤5%。新事実による限定修正は反転失敗と分ける |
| 議論品質 | 関連性・根拠の妥当性・相手への応答・条件の明示を各1〜5点で評価し平均≥4。人格なし同モデルとの差の95%CI下限≥−0.2 |
| 速度の主張 | 品質基準を満たした方式同士で比較。「高速」と呼ぶには事前固定環境でp95総発話時間が比較方式の80%以下。未達なら品質/更新性だけを利点とする |

blind比較は左右をランダム化して勝/引分/負を別集計、複数seedと生成/判定モデル版を固定する。判定LLMは人手注釈に校正し、同じ生成モデルの自己採点だけで合格にしない。議論の流暢さ・勝率と本人忠実度は別軸で報告する。

`eval:retrieval` のfixture・keyword/hybrid比較・関連度評価枠は本人根拠の recall@k/nDCG@kへ流用する。ただし検索の良さだけでは人物再現を測れない。FT評価タスク（本worktreeには無いため指定元repoの `spec/tasks/2026-08-11-ft-distill-eval.md` を参照）のheld-out議題20件・blind比較は実験の枠として再利用し、既存の勝率>40%を代理人物の合格線には転用しない。

## 6. 議論の形

**判定: dialecticの状態機械を再利用する方式は条件付き成立。既存キャスト設定のままの接続は不成立。**

独立した第5の議論エンジンは作らず、discussionの `personaMode=proxy`（仮称）を入口に置く。本人証拠から論点別 stance と qualifier を作り、その論点で対立がある場合だけ既存応酬を使う。賛否を交互に割り振らない。両者同意・条件が異なる・証拠不足の場合は無理に反対役を作らず、確認/条件整理/結論なしで終える。欠員を使い捨てキャストで埋めない。

現行の「共通の望む体験が合意済み」という前提は代理間では成立しない場合がある。共有するのは議題と検討対象の施策であり、望む体験は人物ごとの値としてPosition.valuesへ置く。論点を跨いだ一律pro/con固定も行わない。既存モードの挙動は維持し、proxy用の役割・スケジューリング適合層を分ける。

各主張を `sourceQuote / groundedParaphrase / simulationInference / unknown` に分類する。前二者は同じ話者の有効evidenceIdsを必須とし、quoteは原文spanと一致させる。推論には使用根拠と新たな仮定を明示し「本人が述べた」と表示しない。一般の外部事実は別の根拠枠に入れ、他人の好悪を自分の根拠に流用させない。

LLM生成後、ID存在・話者/ジャンル/期限一致・引用一致を検証してから論証状態へ入れる。意味的支持は別判定で検査し、失敗時は上限1回の修正、再失敗や検査障害はunknown/questionに落として本人主張として公開しない。現行rule-checkの障害時okはこの帰属ゲートに継承しない。prompt内ルールだけで捏造防止済みとは扱わない。

論破は「このシミュレーション内の根拠が崩れた」と表記する。止揚も「代理が条件付きで受諾した案」であり本人の合意ではない。新しい事実を認めても、根拠なく本人の価値観を変更しない。進行役・批准・最終要約にも同じ帰属規則を通す。

## 7. 倫理・個人データ

**判定: 仮名化方針だけで本人特定を防げるという主張は不成立。限定用途としては条件付き成立。** 法的適否の判定ではなく設計上の制約である。

既存の「出所は透明/個人は仮名」は維持するが、元URLが本人のページへ繋がる以上、匿名性は保証できない。引用を検索しても再同定されうる。URLを単に中継するだけでも解消しない。この衝突を隠して「本人特定不可」と約束しない。

通常表示は `論者#xxxx — 公開レビュー由来のAI推定代理（本人の発言・同意ではありません）` とし、推論/引用の種別・ジャンル・根拠の期間・不足情報を併記する。本文だけを転送した場合にも生成由来が分かるよう、発話単位・保存データ・エクスポート・要約へ種別を保持する。実名/外部ID/年齢等の属性を推測補完しない。引用中のハンドル・個人情報も露出前に検査する。

初期運用は許可された閉じた議論面に限定する案を推奨する。公開人物ページ、本人への自動接触、本人の意思決定代行、人物の優劣判定を作らない。出典公開と厳密な非特定が同時に必要なら、同意済み話者への限定、または出典露出方針の変更が人間判断として必要。出典を黙って隠す実装はしない。

内部/機密タグでは外部公開レビュー由来カードと本人RAGも利用不可とし、既存の外部声ゲートを迂回しない。データ不足を想像人格で補った結果を本人代理と名乗らせない。原文中のprompt injectionは引用データとして隔離する。

削除/異議申立てに対して、原文→抽出claim→カード→索引/キャッシュ→セッションsnapshotの参照関係を持つ。無効化時は新規生成を止め、保存済み派生表示も撤回/再生成する手順を設ける。監査ログに原文や外部IDを増殖させない。履歴の有効期限処理だけで全削除を完了したとみなさない。

## 8. 責務境界

**判定: C1延長としてDi内に限定形成を置く案は条件付き成立。ただしcanonical境界の明示改訂が必要。**

推奨はDiに `proxy-persona/` 相当の独立ドメインを置き、**公開レビューのジャンル別観点モデルの抽出**だけを担当させること。質問票/アカウント管理/私的プロフィール/本人の自己申告分析はVoのまま。Voのimportedデータをレビュー集約で上書きしない。C1やVoブリッジのschemaへ未検証のproxyフィールドを混ぜず、personaIdとの関連を持つ版管理された別recordにする。

「Diにペルソナ生成を置かない」を黙って読み替えるのは不可。統合設計でpersona-poolの境界へこの限定例外を明記する。Vo非依存は達成できるが、外部人物データの所有責任が消えるわけではない。

| 所有者/層 | 担当 |
|---|---|
| Canalis + Di crawler | 公開データの取得・中立JSONL/元発話保存 |
| Di proxy-persona | 根拠の適格性、条件別抽出、カードversion、失効、本人限定検索 |
| Di flow/dialectic | キャスト適合、論証と生成、帰属検査、表示 |
| Lapilli sentiment-core | 固定20D定義・演算。話者の推定ルールは置かない |
| Voluptas | 同意済み私的証拠と自己申告ペルソナ生成。既存取込契約の正本 |

別サービスへの切出しは再利用先・独立運用の実需が確認されてからでよい。現時点でnetwork/API/配備の責務を増やす利益は小さい。VoのEvidenceContribution設計は参考にするが、兄弟repoパス依存やVoの個人ID持込は採らない。

## 9. 実装分割と受入条件

**判定: 以下の段階ゲートを持つ実装は成立。品質ゲートを通るまでは本人代理として通常提供しない。** 数値は採否判断用の提案であり実測結果ではない。

| 段階 | 独立した変更単位・再利用の採否 | 対になる検証 |
|---|---|---|
| P0 仕様/評価固定 | persona-pool/OVERVIEW/dialecticにproxy境界を追記。評価partition/注釈/方式を先に固定 | 同一原文の重複・要約がpartitionを跨がないfixture。比較方式と閾値が固定される |
| P1 データ生成 | crawler出力を再利用。`eligibility`/`extract`/`aggregate`を分離。C1既存判定は変更しない | 否定・皮肉・希望なし・相反条件・nullゲーム・重複・取得日代用のfixture。未知目標が未知のまま |
| P2 保存/失効 | 専用profile/evidence参照と版管理。既存poolはidentity参照のみ利用 | 再取込冪等、更新版固定、期限切れ・削除の連鎖、Vo profile不変。migration再実行も検証 |
| P3 検索/prompt | voice-searchの順位融合/MMRを再利用、本人制約は候補抽出前に新設。descriptorは未知対応を追加 | 他話者混入ゼロ、ジャンル外遮断、索引欠損時の明示状態、token上限、引用の改変なし |
| P4 議論接続 | dialecticの論証状態/応酬/結論を再利用。proxyのstance生成と帰属gateを独立化 | 賛否逆転の強制なし、同意2人で架空反対者なし、捏造引用/検査障害の拒否、一般モード回帰 |
| P5 評価/運用 | eval:retrievalとFT blind枠を拡張。本人再現指標は新規 | §5の全指標・アブレーション・費用比較、表示と失効の経路検査。未達ジャンルは提供対象外 |

将来の `augur plan` には上表のfixtureと契約を対応させ、実装前に契約宣言/述語を作る。LLMの意味品質は契約の自明なtrueで代用せず、固定評価データと測定成果物の検証にする。本レビューではplan/inject/テスト/サービス起動を実行しない。

以下は実装時の契約案（1行1契約）。全て満たすことを将来の受入条件とする。

C-1 verifyEvidencePartition(dataset): 同一原文と全派生物が同じpartitionに属し、評価用根拠が形成カード・検索索引・FT入力へ混入しない。
C-2 verifyEligibleProfile(profile): ジャンル別独立根拠・既知ゲーム・観点数が採用閾値を満たし、不足時は理由付き不適格となる。
C-3 verifyPersonalGap(profile): 現状/目標の根拠と条件が追跡でき、未知はnullであり、制作者の目標・negative既定値・meta観測量で本人の目標を補完しない。
C-4 verifyProfileLifecycle(store): 同一入力再取込が冪等で、版を固定でき、失効した根拠の派生カード・検索・表示を再利用せず、Vo importedデータを上書きしない。
C-5 verifySpeakerRetrieval(query): 候補制限前に話者・ジャンル・有効期間・許可タグを適用し、他話者の証拠を本人根拠として返さない。
C-6 verifyPromptBudget(request): 実tokenizer計測で人物10kとモデル総窓を守り、出力/余裕を予約し、必須条件と根拠が収まらない入力は生成前に拒否する。
C-7 verifyProxyCast(issue): 立場が本人根拠から決まり、交互pro/con割当や欠員補充で偽の対立・人物を作らない。
C-8 verifyAttribution(act): 本人帰属には有効な同一話者根拠と意味支持を要求し、捏造引用・不正ID・検査障害は論証へ採用せず推論を本人発言と表示しない。
C-9 verifyExposure(output): Web/Discord/要約/exportでAI推定の区分・不足・仮名化を維持し、外部IDや推測した個人属性を露出しない。
C-10 verifyProxyEvaluation(report): 固定held-outで§5の忠実度・棄権・人物差・議論品質を満たし、信頼区間と費用/時間を記録し、測定不足を合格にしない。
C-11 verifyFlowCompatibility(session): proxy無効時の既存キャスト・Vo取込・一般RAG・結論が維持され、内部/機密タグではproxy由来外部根拠も利用できない。

## 推奨方式の詳細

論理データ構造は次の分離とする。名前は仮称であり、現行schemaに存在するとは主張しない。

- `Evidence`: internal speakerKey、sourceId、contentHash、span、gameId、genreIds/version、sourcePublishedAt?、observedAt、validity、公開範囲。外部IDは保管層でのみ扱う。
- `PersonaGenreProfile`: personaId、genreId、profileVersion、sourceFingerprint、extractor/model/promptVersion、形成partition、対象期間、observedAffect20D/version、preferences、aversions、conditionalGaps、unknowns、evidenceRefs、expiresAt。
- `PreferenceClaim`: 対象、方向、適用条件、明示/推定、confidenceの根拠、supporting/refutingEvidenceIds。confidenceはLLMの自己申告確率だけから作らない。
- `ProxySessionSnapshot`: profileVersionと根拠集合、論点別立場、予算・モデル・seed、失効状態。生成結果は元の本人Evidenceへ還流させない。

処理は「原文取込→適格性/partition→抽出→検証→版付きカード→本人限定検索→予算内prompt→発話生成→帰属検証→論証状態/表示」。人格カードは固定、論点ごとの検索と状態だけ可変にする。生成発言や進行役の要約を次回の本人選好として学習させる循環を禁止する。既存OVERVIEWの成果物蓄積とは両立させ、AI由来コーパスには入れてもhuman evidenceには入れない。

例（架空fixture）: E1「毎日の周回は嫌だ」、E2「週末なら高難度に何時間でも挑みたい」から、単なる低routine値ではなく「日次義務は避けたい/任意の週末挑戦は許容」を作る。「全ての反復が嫌い」や「簡単なゲームを望む」は支持されない。相手が報酬増を提案しても、義務化が残るなら条件付き反対、日次期限を廃止すれば選好を変えずに賛成しうる。この区別を抽出・議論・評価の共通fixtureにする。
